# リポジトリ証拠から完全なテストワークフローを作成する

作成する：`web-e2e/workflows.md`。

現行リポジトリと既存仕様から、意図した行動ワークフローを再構築する。

ワークフローを書く前に、次を検査する：

- `sop/PRD.md`
- `sop/TUC.md`（あれば）
- `sop/NTC.md`（あれば）
- `sop/ECS.md`（あれば）
- `sop/TODO.md`（あれば）
- `prisma/schema.prisma`
- `prisma/seed.ts`
- `docs/api.md`（既にあれば）
- `docs/backend-implementation-plan.md`（あれば）
- `backend/`
- `web/`
- 既存バックエンドテスト
- 既存 web-e2e テスト

Web アプリについて次も検査する：

- ルート表
- ナビゲーション
- インタラクティブコントロール
- フォーム
- 検証
- ダイアログ／シート／ドロワー
- メニュー／コンテキストメニュー
- 検索／フィルタ／ソート
- ページネーション
- 一括選択／操作
- 状態遷移
- メディアコントロール
- インポート／エクスポート
- 空／エラー状態
- 破壊的確認

## 出典の優先順位

意図挙動を決めるときは、次を優先する：

1. `sop/PRD.md`
2. 存在する場合の `sop/TUC.md`／`sop/NTC.md`／`sop/ECS.md`
3. `schema.prisma` の明示ドメイン規則
4. 安定したバックエンド／API 挙動
5. 実装済みのユーザー可視挙動
6. シードシナリオと fixtures
7. 孤立した UI 成果物、または死んだエクスポート／足場コントロール

明らかな実装バグに合わせて意図ワークフローを書き直さない。

未対応の製品機能向けにワークフローを発明しない。

重要な挙動が未解決なら、規則をでっち上げず、関連ワークフローまたは最終の未解決節に短い **未解決の挙動** 注記を入れる。

## ワークフローの目標

これらのワークフローは Playwright の行動受入仕様である。

Playwright ソースコードではない。

読めるワークフロー風疑似コードを使う。

有限だが広い機能カバレッジで製品を覆う。

該当する場合は含める：

- ルートアクセス
- ナビゲーション
- 作成フロー
- 編集フロー
- 削除／アーカイブフロー
- 詳細ビュー
- 検索
- フィルタ
- ソート
- ページネーション
- タブ
- ダイアログ
- シート
- メニュー
- コンテキストメニュー
- 一括操作
- 状態遷移
- 検証失敗
- キャンセル経路
- 空状態
- 確認フロー
- メディア操作
- インポート／エクスポート
- エンティティ横断ナビゲーション
- 重要なエラー経路
- 重要な境界事例

ボタンごとのワークフローより、現実的なエンドツーエンドワークフローを優先する。

シナリオを決定的・再現可能にする箇所ではシードデータを使う。

## 分岐構文

分岐は実条件を記述する。

`{correct/error}` のような汎用分岐を避ける（それらの語がドメインで本当に意味を持つ場合を除く）。

優先：

```text
Login
    enter phone
    enter password

    if password matches:
        submit
        dashboard opens

    if password does not match:
        submit
        login remains open
        error message appears
```

ワークフローは次を使ってよい：

- 前提条件
- 順序
- 選択
- 分岐
- 繰り返し
- 期待される表示結果

実用的で読め、Playwright で直接実装できること。

完成成果物を直接 `web-e2e/workflows.md` へ書く。
