# Figma 生成 Web アプリを再構成する

`web/` 配下の Figma 由来 WorldMan UI を監査し、再構成してください。

まず現状アプリを検査し、次を特定する：

- ルートとページ
- 巨大な TSX
- ページ級コンポーネント
- 共有コンポーネント
- ダイアログ／シート／ドロワー／ポップオーバー
- フォーム
- 表とリスト
- 検索・フィルタ・ソート
- メニューとコンテキストメニュー
- CRUD
- ローカル／mock データ源
- ローカル永続化
- インタラクティブコントロール
- 未完成または死んだコントロール

その後、有用な範囲で構造を再構成する。

## Figma デモ資産のローカル化

Figma Make プロトタイプは、デモ用メディア（画像・フォント・音声・動画・Lottie など）を
外部 URL で参照することが多い。本再構成では UI を自己完結させる：

1. `web/` 内のデモ資産として使われている絶対 `http(s)://` URL を洗い出す
   （CSS `@import` / `@font-face`、`<img>` / `<audio>` / `<video>`、背景 URL、
   メディアの fetch/import など）。
2. 各資産を **そのまま** `web/assets/` 配下へダウンロードし、必要なら種別ごとに
   分ける：
   ```text
   web/assets/
       images/
       fonts/
       audio/
       video/
       …
   ```
   ダウンロード時は、中国本土でよく遮断されるホスト（Google / Google Fonts /
   gstatic、Facebook / fbcdn など）へ到達するため、ローカル HTTP プロキシ
   `http://localhost:8118`（`http_proxy` / `https_proxy`、または curl/wget の
   `--proxy`）を使うこと。直結が失敗しても諦めたり偽資産に置き換えたりせず、
   プロキシ経由で本物のファイルが取れるまで再試行する。
3. 参照をすべてローカルパスまたはモジュール import に書き換える。ファイル名は
   安定で分かりやすく。付属のライセンス／帰属メモがあれば残す。
4. コミットするソースにデモ用 CDN／ストック素材のホットリンクを残さない。
   資産ではない API エンドポイントや意図した第三者連携は対象外でよい。

**ライセンスと真正性（重要）:** Figma プロトタイプ内の外部リンクは、通常かなり
寛容な許諾である。例として Unsplash の写真は
[Unsplash License](https://unsplash.com/license) で、個人・商用とも無料、撮影者の
許可や帰属表記も不要（[参考](https://www.zhihu.com/question/50969084)）。開発や
プロトタイプ検証に特に向いている。本アプリはストック写真ギャラリーではなく、
そうした素材配信サービスとの競合関係にもない。**ライセンス範囲を過剰に解釈しない
こと。** 許可の懸念でダウンロードを飛ばしたり、プレースホルダ・単色ブロック・偽
画像などへ置き換えたりせず、実際の外部資産を `web/assets/` に保存すること。

## ページ抽出

大きすぎる／モノリシックな TSX から、適切なときルート級ページを抽出する。

責務ベースを優先：

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

ファイルが長すぎる場合は**必ず分割**する。長すぎるファイルは、たいていは構造が悪い：サービスやディスカバリなどの分散化メカニズムを使っていない、および／またはツール／サポート用コードを専用の外部ソースへ切り出していないことが原因である。

次の境界で分割する：

- ルート境界
- 機能境界
- 状態の所有者
- 再利用 UI 責務
- ドメイン操作
- 共有サービス／ディスカバリ／ツール支援を専用モジュールへ抽出

構造変更が必要でない限り、既存の見た目と操作モデルを保つ。

## UI テスト容易性の再構成

自動テストと保守のため UI 論理を再構成する。

業務論理を匿名 JSX コールバックへ直接置かない。

匿名コールバックは次のみ：

- 引数の転送
- イベント値の取り出し
- イベントを名前付きハンドラ呼び出しへ適応

悪い例：

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

推奨：

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

イベント由来の挙動では、可能ならイベント抽出とイベント非依存の挙動を分ける。

例：

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

次のような明確な命名を使う：

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

意味のある名前が無い場合を除き、`button1_click` のような視覚位置依存名を避ける。

## プロジェクト `sop/` ワークスペース

本再構成および後続の複雑な構築手順では、`sop/` 配下に作業文書を維持する：

- `sop/TODO.md` をライブのタスク一覧とし、作業の進行に合わせて項目状態を更新する。
- ユーザーが複雑なプロンプトを渡したら、候補テストを速やかに抽出または構成して次へ入れる：
  - `sop/TUC.md` — テストユースケース参照集
  - `sop/NTC.md` — 反用例・ネガティブケース
  - `sop/ECS.md` — エッジケースシナリオ
- 製品要件は `sop/PRD.md`（PRD 手順で作成）。
- 共有ツール／サポートクラスの抽出、および後続の e2e カバレッジ作成では、これらの `sop/` 文書を優先する。

明白な Figma 生成欠陥の修正以外では、この段階で製品挙動を変えない。
