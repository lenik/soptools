# 根据仓库证据编写 PRD

## 先介绍 WorldMan 架构

编写 PRD 之前，先说明并落实本模块的 WorldMan 架构：

- WorldMan 应用类似轻量微服务：每个应用既可**完全独立运行**，也可与对等应用**集成**。
- **独立运行**：本应用可拥有基础数据的**简化本地表**（例如联系人仅姓名/电话）。专用对等应用（如联系人应用）可有更完整模型。
- **集成运行**：对他应用主数据只保存 **cuid2 不透明引用**，通过对方 API 解析；不默认跨库外键。
- 主数据主键统一使用 **`cuid(2)`**，以便独立与集成部署下 id 稳定可迁移。
- 标准布局：`prisma/`、`backend/`、`web/`、`web-e2e/`、可选 `mobile/` / `mobile-e2e/`、`sop/`、`docs/`、`docker/`、`i-local/`、`i-medium/`、`worldman.json`。
- 部署：直接进程、Apache/Nginx 反代、或容器。基准端口 `N` 来自 `wm port -n <name>`（HTTPS = HTTP + 1；bridge 下 web 的 `80`/`443` 除外，详见 SOP README）。

PRD 须在适用处体现上述约束。

## 根据仓库证据产出 PRD

创建或替换 `sop/PRD.md`。

请从仓库本身重建产品规格。

编写 PRD 之前，系统性地检查仓库。

至少审阅（若存在）：

- `web/`
- `sop/`
- `docs/`
- `prisma/`
- `README*`
- `package.json`
- `worldman.json`

检查 Web 应用中的：

- 路由与页面
- 导航结构
- 页面标题与标签
- 表单与字段
- 表格与列
- 对话框、抽屉、面板（Sheet）与菜单
- 搜索/过滤/排序控件
- CRUD 操作
- 批量操作
- 状态/状态控件
- 媒体使用
- mock 数据
- 测试夹具（fixtures）
- 常量/枚举
- 本地存储 / 会话存储 使用
- 校验消息
- 空状态
- 错误状态
- 能揭示预期行为的注释/TODO

不要把每一个偶然的设计导出细节都当作产品需求。

从反复出现、语义明确的证据推断产品意图。

## 证据优先级

来源冲突时，按此顺序优先：

1. `sop/` 下已有明确产品文档（尤其是 `sop/PRD.md`），其次是 `docs/`
2. 已有 Prisma/领域定义
3. 已实现的用户可见行为
4. 稳定的 mock/fixture 数据结构
5. 孤立标签、占位文案或死掉的导出/脚手架控件

不要仅为让 PRD「看起来完整」而发明需求。

若重要需求无法从仓库证据确定，记入 **待决问题 / 未解决需求**。

不要因请求澄清而阻塞本任务。

## PRD 要求

PRD 应适于实现与后续验收测试。

在证据支持处覆盖（使用中文目录，勿依赖英文 TOC）：

- 产品概述
- 目标
- 范围
- 范围外
- 术语
- 用户角色
- 领域概念
- 核心实体
- 实体关系
- 业务规则
- 生命周期/状态转换
- CRUD 行为
- 搜索
- 过滤
- 排序
- 分页（如相关）
- 批量操作
- 导入/导出（如相关）
- 媒体
- 历史/审计（如相关）
- 外部引用
- 校验规则
- 删除/归档行为
- 空状态
- 错误行为
- 重要边界情况
- 主要 UI 工作流
- 非功能期望
- WorldMan 独立运行与集成模型
- 待决问题 / 未解决需求

对每条有实质意义的推断需求，写到另一名开发者足以实现或测试的清晰程度。

证据支持时，记录 WorldMan 约束：

- 本模块的独立 vs 集成运行方式
- 哪些实体是本模块拥有的主数据，哪些是对等模块的不透明 cuid2 引用
- 主数据主键使用 `cuid(2)`
- 相关时的部署/端口期望（通过 `wm port -n <name>`；HTTPS = HTTP + 1，bridge 的 `80`/`443` 除外）

在文档化时不要重新设计现有产品。

当证据或提示产出可测试材料时，亦在 `sop/` 下初始化或更新：

- `TODO.md` — 剩余重建 / 实现任务；保持状态最新
- `TUC.md` — 测试用例参考集
- `NTC.md` — 反用例 / 负面测试用例
- `ECS.md` — 边界场景

这些文件供后续 e2e 工作流与工具类/支撑类工作使用。

将完成产物直接写入 `sop/PRD.md`。
