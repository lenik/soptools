# 基于仓库准备后端实现

这是 GPT 步骤（通常会生成后端实现提示词）的 Codex 回退方案。

因为你已在仓库内操作，不要生成打算再粘贴回 Codex 的提示词。

改为检查仓库并准备具体实现计划，再把仓库置于可进入后端实现步骤的状态。

至少审阅：

- `sop/PRD.md`
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `sop/TODO.md`（若存在）
- `prisma/schema.prisma`
- `prisma/seed.ts`
- `web/`
- `package.json`
- `pnpm-workspace.yaml`
- 已有 `backend/`

同时检查：

- Web 路由
- 前端数据/服务抽象
- mock 数据
- 已有请求/响应形状
- 领域枚举与状态转换
- 搜索/过滤/排序行为
- 批量操作
- 跨实体导航
- 看起来可在当前 UI 之外复用的功能

抽取共享工具类或支撑类时，优先采用已在 `sop/` 下记录的需求与场景（`PRD.md`、`TUC.md`、`NTC.md`、`ECS.md`）。

随计划条目完成或推迟，保持 `sop/TODO.md` 状态最新。
创建 `docs/backend-implementation-plan.md`。

## 后端假设

目标：

- `pnpm`
- Node.js
- TypeScript

API 前缀：`/api/v1/`

后端必须暴露有用的领域能力，而不仅是当前 Web UI 所需的最小端点。

对每个领域资源，评估是否确实需要：

- CRUD
- 列表
- 详情
- 搜索
- 查找
- 自动补全
- 过滤
- 排序
- 分页
- 批量获取
- 批量创建/更新/删除
- 关系遍历
- 树遍历
- 状态转换
- 历史
- 版本访问
- 校验
- 统计
- 聚合
- 导入
- 导出
- 媒体操作
- 外部引用解析

不要机械地为每个模型规定全部能力。

计划应定义：

- 后端架构
- 领域/服务边界
- 路由分组
- 校验策略
- 错误模型
- 序列化约定
- 分页约定
- 过滤/排序约定
- 资源能力
- 领域特定操作
- 批量操作语义
- 测试策略
- 与 web/ 的集成关注点
- 实现顺序

优先分离：

- 路由/控制器层
- 校验
- 服务/领域逻辑
- 数据访问
- 共享错误
- API 序列化

不要把领域逻辑直接放在路由处理函数中。

## 基于仓库的缺口处理

若 `sop/PRD.md`、`schema.prisma`、seed 数据与 Web 应用不一致：

- 在 `docs/backend-implementation-plan.md` 中记录矛盾
- 标明哪个来源看起来权威及原因
- 选择最小、可逆的实现假设
- 不要默默重新设计 schema 或产品

若存在 `prisma/request-for-refactor.md`，审阅并将相关阻塞项纳入实现计划，但除非后续实现步骤明确授权，否则不要自动改 schema。

除非调用本文件的工作流明确要求合并规划与实现，否则本步不要实现后端。
