# 重构 Figma 生成的 Web 应用

审计并重构 `web/` 下由 Figma 导出的 WorldMan UI。

先检查当前应用并识别：

- 路由与页面
- 过大的 TSX 文件
- 页面级组件
- 共享组件
- 对话框、面板（Sheet）、抽屉与弹出层（Popover）
- 表单
- 表格与列表
- 搜索、过滤、排序行为
- 菜单与上下文菜单
- CRUD 操作
- 本地/mock 数据源
- 本地持久化
- 交互控件
- 未完成或失效控件

然后在有用处重构结构。

## 页面抽取

在合适时从过大或单体 TSX 中抽出路由级页面。

优先按职责组织：

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

文件过长则**必须拆分**。文件过长通常说明结构不合理：没有使用服务、发现等分散化机制，以及/或者工具/支持类代码本应提取到外部专门的源文件。

按以下边界拆分：

- 路由边界
- 功能边界
- 状态所有权
- 可复用 UI 职责
- 领域操作
- 共享服务 / 发现 / 工具支持抽到专门模块

除非结构变更必要，否则保持既有视觉设计与交互模型。

## UI 可测试性重构

重构 UI 逻辑，便于自动化测试与维护。

业务逻辑不得直接写在匿名 JSX 回调中。

匿名回调仅可：

- 转发参数
- 提取事件值
- 将事件适配为具名处理函数调用

反例：

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

推荐：

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

对基于事件的行为，在可行时把事件提取与事件无关的行为分开。

示例：

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

使用清晰命名，例如：

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

避免不必要地绑定到视觉位置的命名（如 `button1_click`），除非没有更有意义的语义名。

## 项目 `sop/` 工作区

在本重构及后续复杂构建步骤中，于 `sop/` 下维护工作文档：

- 将 `sop/TODO.md` 作为实时任务清单；随工作推进更新条目状态。
- 当用户给出复杂提示时，尽快把候选测试提取或构造进：
  - `sop/TUC.md` — 测试用例参考集
  - `sop/NTC.md` — 反用例 / 负面测试用例
  - `sop/ECS.md` — 边界场景
- 产品需求位于 `sop/PRD.md`（在 PRD 步骤编写）。
- 抽取共享工具类/支撑类以及后续编写 e2e 覆盖时，优先使用这些 `sop/` 文档。

本阶段不要改变产品行为，除非修复明显的 Figma 生成缺陷。
