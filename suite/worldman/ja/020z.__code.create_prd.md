# リポジトリ証拠から PRD を作成

## WorldMan アーキテクチャ（最初に読む）

PRD を書く前に、次のモジュールアーキテクチャを紹介し、適用する：

- WorldMan アプリは軽量マイクロサービス風モジュール：各アプリは**完全に独立**して動かすことも、対等アプリと**統合**することもできる。
- **独立（Standalone）**：アプリは共有基礎データ（例：連絡先の氏名＋電話のみ）の**最小ローカル表**を持ってよい。専用の対等アプリ（例：連絡先）は同じ概念をより完全にモデル化できる。
- **統合（Integrated）**：対等マスタデータは**不透明な cuid2 参照**としてのみ保持し、その対等アプリの API で解決する——横断 DB の外部キーではない。
- マスタデータの主キーは **`cuid(2)`** とし、独立／統合のどちらでもアイデンティティを安定に保つ。
- 標準レイアウト：`prisma/`、`backend/`、`web/`、`web-e2e/`、任意の `mobile/` / `mobile-e2e/`、`sop/`、`docs/`、`docker/`、`i-local/`、`i-medium/`、`worldman.json`。
- デプロイは直接プロセス、Apache/Nginx リバースプロキシ、またはコンテナ。基準ポート `N` は `wm port -n <name>`（HTTPS = HTTP+1、例外は bridge web `80`/`443`；SOP README 参照）。

証拠が支える箇所では、これらの制約を PRD に反映する。

## リポジトリから再構成

`sop/PRD.md` を作成または置換する。

リポジトリ自体から製品仕様を再構成する。

PRD を書く前に、リポジトリを系統的に調べる。

少なくとも次をレビューする（存在すれば）：

- `web/`

- `docs/`
- `prisma/`
- `README*`
- `package.json`
- `worldman.json`

Web アプリについて調べる：

## UI 構造 vs エクスポートノイズ

`sop/design-inventory.md` を**ナビおよび表形式 UI 構造**（ルート、タブ、主要 chrome、
そこに列挙されたダイアログ）の**権威**として扱う。

- ステータス `kept` / `moved` の各インベントリエントリは、任意の装飾ではなく、
  PRD に文書化すべき製品サーフェス（ワークフロー＋受入）である。
- 証拠とともにインベントリを `dropped:<reason>` または `dead`/`scaffold` へ
  更新せずに、列挙済みタブ／ルートを「偶然のエクスポート」へ降格しない。
- 「偶然のデザインエクスポート詳細」は、ラベルのないスタブ、重複足場 chrome、
  またはインベントリが既に `dead`/`scaffold` とマークしたコントロールに適用する——
  実ラベル／内容のある固有画面やタブパネルには適用しない。

残りの製品意図は、反復されセマンティックに意味のある証拠から推論する。

## 証拠の優先順位

ソースが食い違うときは、次の順で好む：

1. `sop/` 下の既存の明示的製品文書（特に `sop/PRD.md`）、次いで `docs/`
2. ルート、タブ、chrome、列挙ダイアログについては `sop/design-inventory.md`
3. 既存の Prisma／ドメイン定義
4. 実装済みのユーザー可視挙動
5. 安定したモック／フィクスチャデータ構造
6. 孤立したラベル、プレースホルダ文、または死んだエクスポート／足場コントロール（インベントリで kept でない場合のみ）

PRD を見た目よく完成させるためだけに要件を発明しない。

重要な要件がリポジトリ証拠から決められない場合は、**未解決の質問／未解決要件**の下に記録する。

明確化を求めてタスクをブロックしない。

## PRD 要件

PRD は実装と後続の受入テストに適すべきである。

証拠が支える範囲でカバーする：

- 製品概要
- 目標
- スコープ
- スコープ外
- 用語
- ユーザーロール
- ドメイン概念
- コアエンティティ
- エンティティ関係
- ビジネスルール
- ライフサイクル／状態遷移
- CRUD 挙動
- 検索
- フィルタ
- ソート
- 該当する場合のページネーション
- 一括操作
- 該当する場合のインポート／エクスポート
- メディア
- 該当する場合の履歴／監査挙動
- 外部参照
- 検証ルール
- 削除／アーカイブ挙動
- 空状態
- エラー挙動
- 重要なエッジケース
- 主要 UI ワークフロー
- 非機能期待
- WorldMan 独立 vs 統合モデル
- 未解決の質問／未解決要件

実質的に推論した各要件について、別の開発者が実装またはテストできるほど明確にする。

証拠が支える場合、WorldMan 制約を文書化する：

- 本モジュールの独立 vs 統合運用
- どのエンティティが所有マスタデータで、どれが対等モジュールへの不透明 cuid2 参照か
- マスタデータ主キーの `cuid(2)` アイデンティティ
- 該当する場合の `wm port -n <name>` によるデプロイ／ポート期待（HTTPS = HTTP+1、例外は bridge `80`/`443`）

文書化しながら既存製品を再デザインしない。

証拠またはプロンプトがテスト可能な材料を生んだら、`sop/` 下も初期化または更新する：

- `TODO.md` — 残りの再構成／実装タスク；状態を最新に保つ
- `TUC.md` — テストユースケース参照集
- `NTC.md` — 反用例・ネガティブケース
- `ECS.md` — エッジケースシナリオ

これらのファイルは後続の e2e ワークフローとツール／サポートクラス作業の入力になる。

完成した成果物を直接 `sop/PRD.md` に書く。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop020]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
