# リポジトリと PRD から Prisma スキーマを作成

作成する：

- `prisma/schema.prisma`
- `prisma/comments.sql`

対象は PostgreSQL。

リポジトリ証拠からデータモデルを導出する。

スキーマ設計の前に調べる：

- `sop/PRD.md`
- `sop/design-inventory.md`（UI が含意する表／カラムとモックエンティティ）
- `web/`
- 存在すれば `sop/figma-archive/`
- 既存の `prisma/` ファイル
- モックデータ
- フィクスチャ
- 型／インタフェース
- 存在すれば API／サービス定義

`sop/PRD.md` があれば一次製品仕様として扱うが、明らかな矛盾については現在のアプリと
デザインインベントリで検証する。インベントリ／モックにデータ付きの表／リストとして
現れるエンティティを、PRD の散文が薄いという理由だけで省略しない。

## モデリング規則

要件：

- ID 列に `cuid(2)` を使う
- データベース表名に `snake_case` を使う
- データベース列名に `snake_case` を使う
- 意味のある Prisma ドキュメントコメントを含める
- 関連する Prisma コメントを PostgreSQL `COMMENT ON` 文へ変換する
- PostgreSQL スキーマ `<appname>` を使う

1画面にすぐ見えるフィールドだけでなく、リポジトリ証拠が支える完全なドメインをモデル化する。

考慮する：

- エンティティのアイデンティティ
- ライフサイクル／状態
- 親子関係
- 多対多関係
- 並び順
- バージョン／履歴の必要性
- メディア
- 外部参照
- 検索／フィルタパターン
- 一意性ルール
- アーカイブ／削除の意味論
- タイムスタンプ
- 実際に必要な拡張性

一般的な検索・ルックアップ経路に有用なインデックスを使う。

ドメイン証拠が支える場合にのみユニーク制約を追加する。

アプリ横断識別子は通常、既存リポジトリ要件が明確に関係を要求しない限り、
DB 外部キー制約なしのスカラー cuid2 フィールドとする。

WorldMan の独立 vs 統合モデリングを支える：所有マスタデータはこのスキーマにあり；
対等マスタデータは API で解決する不透明 cuid2 参照のまま。対等なしで独立実行が必要な
ときのみ最小ローカル表を好む。

安定した関係構造が明らかなとき JSON を避ける。

構造が本当に動的・拡張指向、または安定した関係モデリングに不向きなときのみ JSON を使う。

## 不確実性の扱い

スキーマを精巧に見せるためだけにドメイン構造を発明しない。

重要なモデリング決定にリポジトリ証拠が足りない場合：

- 最も破壊が少なく、最も可逆な表現を選ぶ
- 有用なら Prisma コメントに不確実性を文書化する
- 裏付けのないビジネスルールを黙って断定しない

本手順では `seed.ts` を生成しない。

完成ファイルを直接次へ書く：

- `prisma/schema.prisma`
- `prisma/comments.sql`
