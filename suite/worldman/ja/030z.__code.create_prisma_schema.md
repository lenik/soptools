# リポジトリと PRD から Prisma スキーマを作成する

作成：

- `prisma/schema.prisma`
- `prisma/comments.sql`

対象は PostgreSQL。

リポジトリ証拠からデータモデルを導く。

スキーマ設計の前に、次を検査する：

- `sop/PRD.md`
- `web/`
- 既存 `prisma/` ファイル
- mock データ
- フィクスチャ
- 型／インタフェース
- 存在すれば API／サービス定義

`sop/PRD.md` があれば主要製品仕様として扱うが、現行アプリと照合し明らかな矛盾を確認する。

## モデリング規則

要件：

- ID 列は `cuid(2)`
- DB 表名は `snake_case`
- DB 列名は `snake_case`
- 意味のある Prisma ドキュメントコメントを付ける
- 関連コメントを PostgreSQL `COMMENT ON` に変換する
- PostgreSQL schema `<appname>`

ある画面で直ちに見えるフィールドだけでなく、リポジトリ証拠が支えるドメイン全体をモデル化する。

考慮する：

- エンティティ同一性
- ライフサイクル／状態
- 親子関係
- 多対多関係
- 並び順
- バージョン／履歴の必要性
- メディア
- 外部参照
- 検索／フィルタパターン
- 一意性規則
- アーカイブ／削除セマンティクス
- タイムスタンプ
- 実際に必要な拡張性

よくあるルックアップと検索パスに有用な索引を付ける。

UNIQUE はドメイン証拠が支えるときだけ付ける。

アプリ横断識別子は、既存リポジトリ要件が明確にリレーションを要求しない限り、通常は DB 外部キーなしのスカラー cuid2 フィールドとする。

WorldMan の独立 vs 統合モデリングを支える：所有マスタはこの schema に置き、対等マスタは API で解決する不透明 cuid2 参照のままにする。対等アプリなしで単独実行が必要なときだけ、最小ローカル表を優先する。

安定した関係構造が明らかなときは JSON を避ける。

構造が真に動的、拡張向き、または安定関係モデリングに不向きなときだけ JSON を使う。

## 不確実性の扱い

スキーマを「豊かに」見せるためだけにドメイン構造を発明しない。

重要なモデリング判断にリポジトリ証拠が足りない場合：

- 破壊が最も少なく、最も可逆な表現を選ぶ
- 有用なら Prisma コメントに不確実性を記す
- 根拠のない業務ルールを黙って断言しない

この手順では `seed.ts` を生成しない。

完成ファイルを直接次へ書く：

- `prisma/schema.prisma`
- `prisma/comments.sql`
