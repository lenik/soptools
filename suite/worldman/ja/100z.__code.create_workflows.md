## ソース優先順位

意図挙動を決めるとき、次を好む：

1. `sop/PRD.md`
2. 存在すれば `sop/TUC.md` / `sop/NTC.md` / `sop/ECS.md`
3. `schema.prisma` の明示的ドメインルール
4. 安定したバックエンド／API 挙動
5. 実装済みのユーザー可視挙動
6. シードシナリオとフィクスチャ
7. 孤立した UI 成果物または死んだエクスポート／足場コントロール

明らかな実装バグに合わせるためだけに意図ワークフローを書き換えない。

未サポートの製品機能向けにワークフローを発明しない。

重要な挙動が未解決なら、ルールを捏造するのではなく、関連ワークフローまたは
最終の未解決セクションに短い **Unresolved behavior** 注記を含める。

## ワークフローの目標

これらのワークフローは Playwright 向けの行動受入仕様である。

Playwright ソースコードではない。

読みやすいワークフロー風疑似コードを使う。

有限だが幅広い機能カバレッジで製品をカバーする。

該当する場合、含める：

- ルートアクセス
- ナビ
- 作成フロー
- 編集フロー
- 削除／アーカイブフロー
- 詳細ビュー
- 検索
- フィルタ
- ソート
- ページネーション
- タブ
- ダイアログ
- シート
- メニュー
- コンテキストメニュー
- 一括操作
- 状態遷移
- 検証失敗
- キャンセル経路
- 空状態
- 確認フロー
- メディア操作
- インポート／エクスポート
- エンティティ横断ナビ
- 重要なエラー経路
- 重要な境界ケース

ボタンごとの1ワークフローより、現実的な end-to-end ワークフローを好む。

シナリオを決定的・再現可能にする箇所ではシードデータを使う。

## ブランチ構文

ブランチは実条件を記述すべきである。

それらの用語がドメインで本当に意味を持たない限り、`{correct/error}` のような
汎用ブランチを避ける。

好む例：

```text
Login
    enter phone
    enter password

    if password matches:
        submit
        dashboard opens

    if password does not match:
        submit
        login remains open
        error message appears
```

ワークフローは次を使ってよい：

- precondition
- sequence
- selection
- branch
- repeat
- expected visible result

実用的で読みやすく、Playwright で直接実装可能なままにする。

完成した成果物を直接 `web-e2e/workflows.md` に書く。

インベントリ裏付けのタブ付きサーフェスが異なるユーザータスクを持つ場合、
それらを演習するワークフローを含める——二次タブを一度も開かない単一の
ハッピーパスに潰さない。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop100]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
