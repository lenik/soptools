# Web とバックエンドの統合

`web/` を `backend/` に接続し、UI が実 API を使うようにする。

## 目標

- 適切な箇所で、デモ、モック、ローカル専用データ元をバックエンド API に置き換える。
- 承認済みの UI 構造と視覚デザインを保つ。統合中だからといってアプリを再デザインしない。
- 明確なフロントエンド API／サービス層を導入する（`web/src/services/` または同等の
  クライアントモジュールを好む）。ページコンポーネントに生の `fetch()` 呼び出しを散らさない。
- `sop/design-inventory.md` を再確認する：すべての `kept`/`moved` ルートとタブは、
  統合後も主要コンテンツを描画しなければならない（seed／API が空だからといって
  恒久的な空テーブルにしない）。

## シードカバレッジゲート（モック削除前）

1. `sop/seed-coverage.md` を読む（無ければ `040` の規則で作成／更新する）。
2. ユーザー可視のリスト／表／詳細に供給する各モック元について：
   - `prisma db seed`（またはプロジェクトのシードコマンド）後、API + seed が
     同等の代表行（名前、件数、メディア、状態）を返せることを確認する。
   - **致命的ギャップ**が残る場合は、先に `prisma/seed.ts`／バックエンドを直すか、
     そのサーフェス用の一時ローカルフォールバックを残し、`sop/TODO.md` +
     `seed-coverage.md` に文書化する。
3. 以前 Figma デモデータを示していたサーフェスについて、モックを削除して UI を
   空のままにしては**ならない**。

所与のソースについてゲートが通ったあとでのみ、そのソースを API に置き換える。

## UI 挙動

UI が次のケースを正しく扱うことを確認する：

- loading
- empty state（ドメインが本当に空のときのみ——seed が遅れたときではない）
- server error
- validation error
- not found
- conflict
- save success
- delete/archive confirmation
- refresh
- reload persistence
- search
- filter
- sort
- pagination

ドメインに合う場合、大規模または再利用可能なデータセットではサーバー側挙動を好む。

## 統合がバックエンド問題を露出したとき

統合が本物のバックエンド設計問題を露出したら、必要に応じてバックエンドを再構成する。
バックエンド挙動が変わるとき：

- バックエンドテストを更新する
- 公開 API の一貫性を保つ
- バックエンドテストを再実行する

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop080]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
