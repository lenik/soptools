# Web をバックエンドと統合する

`web/` を `backend/` に接続し、UI が実 API を使うようにする。

## 目標

- 適切な箇所で、デモ・モック・ローカル専用データ元をバックエンド API に置き換える。
- 承認済みの UI 構造と視覚デザインを保つ。統合中だからといってアプリを再設計しない。
- 明確なフロントエンド API／サービス層を導入する（`web/src/services/` または同等の
  クライアントモジュールを好む）。生の `fetch()` 呼び出しをページコンポーネントに散らさない。
- `sop/design-inventory.md` を再確認する：`kept`／`moved` の各ルートとタブは、統合後も
  主要コンテンツを描画しなければならない（seed／API が空だからといって恒久的な空表にしない）。

## Seed カバレッジゲート（モック削除前）

1. `sop/seed-coverage.md` を読む（無ければ `040` の規則で作成／更新する）、
   **Discrepancy log** を含む。
2. ユーザー可視のリスト／表／詳細を供給する各モック元について：
   - `prisma db seed`（またはプロジェクトの seed コマンド）後に、API＋seed が同等の
     代表行（名前、件数、メディア、状態）を返せることを確認する。
   - **media ↔ text** ペアが Figma モックが示したものとまだ一致することを確認する
     （ポスター／タイトルの入れ替えなし）。`mismatched` 行は、モック削除前に修正か
     明示的な discrepancy エントリが必要。
   - 重要サーフェス上のステータス `missing` または未解決の `schema-blocked` は
     ゲート失敗。`figma-suspect` はログされた根拠があれば進行してよい。
     `seed-enriched` は元の Figma 行が残っていれば問題ない。
   - **重要なギャップ**が残る場合は、先に `prisma/seed.ts`／バックエンドを直すか、
     そのサーフェス用の一時的なローカルフォールバックを残し、`sop/TODO.md` と
     `seed-coverage.md` に記録する。
3. 以前 Figma デモデータを表示していたサーフェスを、モックを削除して UI を空のままに
   **してはならない**。

あるソースについてゲートが通った後にのみ、そのソースを API に置き換える。

## UI 挙動

UI が次のケースを正しく扱うことを確認する：

- 読み込み中
- 空状態（ドメインが本当に空のときのみ——seed が遅れているときではない）
- サーバエラー
- 検証エラー
- not found
- 競合
- 保存成功
- 削除／アーカイブ確認
- 再読込
- リロード永続化
- 検索
- フィルタ
- ソート
- ページネーション

大規模または再利用可能なデータセットでは、ドメインに合うならサーバ側挙動を好む。

## 統合がバックエンドの問題を露呈したとき

統合が実バックエンド設計の問題を露呈したら、必要に応じてバックエンドを再構成する。
バックエンド挙動が変わるとき：

- バックエンドテストを更新する
- 公開 API の一貫性を保つ
- バックエンドテストを再実行する

## SOP 駆動コミット

**本手順が進むにつれて**コミットする——まとまったスライスごと（成果物の書き出し、
1ルート／機能の抽出、1モックの置換、一部テストが green、…）。手順全体を末尾の
単一コミットに**先送りしてはならない**。

SOP 駆動の件名は `[sop080]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
