## バックエンド前提

対象：

- `pnpm`
- Node.js
- TypeScript

API 接頭辞：`/api/v1/`

バックエンドは、現在の Web UI が必要とする最小エンドポイントだけでなく、
有用なドメイン能力を公開しなければならない。

各ドメインリソースについて、次が意味のある必要かを評価する：

- CRUD
- list
- detail
- search
- lookup
- autocomplete
- filtering
- sorting
- pagination
- batch retrieval
- bulk create/update/delete
- relation traversal
- tree traversal
- state transitions
- history
- version access
- validation
- statistics
- aggregation
- import
- export
- media operations
- external reference resolution

すべてのモデルに機械的にすべての能力を処方しない。

計画は次を定義すべきである：

- バックエンドアーキテクチャ
- ドメイン／サービス境界
- ルートグループ
- 検証戦略
- エラーモデル
- シリアライゼーション規約
- ページネーション規約
- フィルタ／ソート規約
- リソース能力
- ドメイン固有操作
- 一括操作の意味論
- テスト戦略
- web/ との統合懸念
- 実装順序

次の分離を好む：

- ルート／コントローラ層
- 検証
- サービス／ドメインロジック
- データアクセス
- 共有エラー
- API シリアライゼーション

ドメインロジックをルートハンドラに直接置かない。

## リポジトリ根拠のギャップ処理

`sop/PRD.md`、`schema.prisma`、シードデータ、Web アプリが食い違う場合：

- 矛盾を `docs/backend-implementation-plan.md` に記録する
- どのソースが権威に見え、なぜかを特定する
- 最も小さく可逆な実装仮定を選ぶ
- スキーマや製品を黙って再デザインしない

`prisma/request-for-refactor.md` または `sop/Backend amends.md` がある場合はレビューし、
関連する blocking 項目を実装計画に織り込む。スキーマとバックエンドの修正は
バックエンド実装時に適用し、それらのファイルをマージしてから削除する。

このファイルを呼び出すワークフローが計画と実装の結合を明示的に求めない限り、
本手順でバックエンドを実装しない。

ソースが食い違うとき、ユーザー可視サーフェスについては `sop/design-inventory.md` +
現在の `web/` 挙動を、永続化形状については `schema.prisma` / seed を好み——
疎な API 計画に合わせて UI を薄くするのではなく、衝突を記録する。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop050]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
