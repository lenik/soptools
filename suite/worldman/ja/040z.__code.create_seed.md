## 発明より抽出を好む

スキーマが表現できる限り、シード行は **Figma／web デモデータを保全**すべきである：

1. `sop/design-inventory.md` に列挙されたすべてのモック／デモ／フィクスチャ元と、
   まだ `web/` または `sop/figma-archive/` 下にあるものを特定する。
2. 名前／形状が揃うとき、それらのレコードをフィールドごとに Prisma モデルへ写す。
3. プロジェクトに既にある安定したデモ概念、名前、カテゴリ、メディア参照、
   代表状態を再利用する。
4. 新しい行を発明するのは、`sop/TUC.md` / `sop/ECS.md` またはスキーマ必須の関係が
   要求するギャップ埋めに限る——既存デモ内容をより薄い「クリーン」サンプルに
   置き換えるためではない。
5. モックエンティティがスキーマに収まらない場合は、デモを黙って落とすのではなく
   `prisma/request-for-refactor.md` を提出する（または Open Questions に記す）。

`sop/TUC.md` / `sop/ECS.md` シナリオを再現可能にするシード行を好む。

|-------------|------------------|--------------------------------|-------------------|-----|

すべてのインベントリモック元が現れるべきである。ギャップは明示する。手順 `080` は
未カバーの致命的ギャップが残るモックの削除を拒否する。

## シードの目標

シードは行を埋める以上のことをすべきである。次に十分なドメイン演習を行う：

- ローカル開発
- UI 統合
- API テスト
- Playwright ワークフロー
- 検索／フィルタ／ソートのデモンストレーション
- 状態遷移テスト

該当する場合、含める：

- 複数の代表エンティティ
- 複数のカテゴリ／型
- 現実的な関係
- 異なるライフサイクル状態
- アクティブ／非アクティブ例
- draft／published／completed／cancelled 例
- 親子関係
- 多対多関係
- 履歴／バージョン例
- 空または任意フィールドの例
- テストに有用な境界例
- 検索／フィルタで区別できる値
- 日時のバリエーション
- デモメディア URL
- 画像 URL
- 該当する場合の音声／動画 URL
- 該当する場合のファイル／添付

ランダムデータより、決定的で読みやすいデモ値を好む。

テストが予測可能なレコードを必要とする場合、安定した識別子または安定した
ルックアップキーを使う。

本手順中に `prisma/schema.prisma` を変更したり黙って再デザインしたりしない。

成果物：`prisma/seed.ts` と `sop/seed-coverage.md`。

<optional title="Also request schema / backend amends?">
本シード作業が既存のバックエンド設計プロンプトまたは既存 `backend/` ツリーに対する
ギャップを露出した場合、必要な修正ファイルを書く（不要なものは省略）：

1. **Schema** — `schema.prisma` が要件、関係、ライフサイクル状態、制約、履歴ケース、
   または現実的なテストを表現できないとき `prisma/request-for-refactor.md`。
   影響モデル、証拠、シードシナリオ、不十分な理由、深刻度（blocking | recommended）、
   最小変更、およびデータ／シード／API／テストへの影響を含める。

2. **Backend** — それらの発見に合わせるためバックエンド設計プロンプトまたは
   既存 `backend/` が API／挙動変更を必要とするとき `sop/Backend amends.md`。

ここでは変更を**適用しない**。後続の実装がこれらのファイルをマージし、
その後削除すべきである。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

`CHECKPOINT.md` を参照。
