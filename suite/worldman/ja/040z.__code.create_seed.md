# リポジトリ状態からシードデータを作成する

作成する：`prisma/seed.ts`。

既存リポジトリを事実の源泉とする。

シードを書く前に、次を検査する：

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/TUC.md`（あれば）
- `sop/NTC.md`（あれば）
- `sop/ECS.md`（あれば）
- `web/`
- 既存 fixtures
- mock データ
- デモデータ
- テスト

適切な場合、プロジェクトに既にある安定したデモ概念、名称、カテゴリ、メディア参照、代表状態を再利用する。

`sop/TUC.md`／`sop/ECS.md` のシナリオを再現しやすくするシード行を優先する。
## シードの目標

シードは行を埋めるだけであってはならない。次を十分支える程度にドメインを鍛える：

- ローカル開発
- UI 統合
- API テスト
- Playwright ワークフロー
- 検索／フィルタ／ソートのデモ
- 状態遷移テスト

該当する場合は含める：

- 複数の代表エンティティ
- 複数のカテゴリ／タイプ
- 現実的な関係
- 異なるライフサイクル状態
- 有効／無効の例
- 下書き／公開／完了／取消の例
- 親子関係
- 多対多関係
- 履歴／バージョンの例
- 空または任意フィールドの例
- テストに有用な境界例
- 検索／フィルタで区別できる値
- 日付／時刻のバリエーション
- デモ用メディア URL
- 画像 URL
- 該当時の音声／動画 URL
- 該当時のファイル／添付

乱数より、決定的で読めるデモ値を優先する。

テストが予測可能なレコードを必要とし得る箇所では、安定識別子または安定ルックアップキーを使う。

この手順では `prisma/schema.prisma` を変更したり、黙って再設計したりしない。

成果物: `prisma/seed.ts`。
