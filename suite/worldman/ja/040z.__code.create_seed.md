# リポジトリ状態から seed データを作成

`prisma/seed.ts` を作成する。

既存リポジトリを真実源として使う。

seed を書く前に調べる：

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/design-inventory.md`（特に **Mock / demo data sources**）
- `sop/seed-coverage.md`（既存 seed を更新する場合）
- `sop/TUC.md`（存在すれば）
- `sop/NTC.md`（存在すれば）
- `sop/ECS.md`（存在すれば）
- `sop/figma-archive/`（存在すれば）
- `web/`
- 既存フィクスチャ
- モックデータ
- デモデータ
- テスト

## 発明より抽出を優先

seed 行は、スキーマが表現できる限り **Figma／web デモデータを保全**すべきである：

1. `sop/design-inventory.md` に列挙されたすべてのモック／デモ／フィクスチャ元と、
   `web/` または `sop/figma-archive/` 下に残るその他を特定する。
2. 名前／形状が揃うとき、それらのレコードをフィールド単位で Prisma モデルへ写す。
3. プロジェクトに既にある安定したデモ概念、名前、カテゴリ、メディア参照、
   代表状態を再利用する。
4. **media ↔ text ペアをまとめて保つ**（画像／ポスターとそのタイトル、キャプション、
   著者、価格など）。Figma 画像を別の発明タイトルに付けたり、既存デモ名に新しい
   ヒーロー画像を発明したりしてはならない。
5. 新行の発明は `sop/TUC.md`／`sop/ECS.md` またはスキーマ必須の関係で必要なギャップを
   埋めるためだけ——既存デモ内容を薄い「クリーン」なサンプル集合で置き換えるためではない。
   発明した各行をカバレッジ報告でマークする。
6. モックエンティティがスキーマに収まらない場合は、デモを黙って落とすのではなく
   `prisma/request-for-refactor.md` を書く（または Open Questions に記す）。
7. Figma／モックデータ自体が誤って見える場合（重複名、壊れた URL、隣接 UI コピーと矛盾する
   プレースホルダ lorem、明らかに別カードのものに見える画像）、seed で黙って
   「修正」しては**ならない**。そのまま抽出することを好み、その後
   `figma-suspect` の discrepancy を記録する（下記）。スキーマまたは実行時が
   それ以外で壊れる場合に限り、seed は最小限の補正を載せてよい——その補正は
   文書化しなければならない。

Figma デモ集合を消さ**ずに**、`sop/TUC.md`／`sop/ECS.md` シナリオを再現できる
seed 行を好む。

## Seed カバレッジ報告（必須）

`sop/seed-coverage.md` を書く／更新する：

```markdown
# Seed coverage vs web / Figma mocks

| mock source | entity / concept | mock examples (count or names) | seed model / rows | status | media↔text |
|-------------|------------------|--------------------------------|-------------------|--------|------------|
| …           | …                | …                              | …                 | matched / seed-enriched / figma-suspect / schema-blocked / missing | ok / mismatched / n/a |

## Discrepancy log (required when anything is not `matched`)

| id | status | evidence (mock path / UI) | seed choice | why (figma issue vs seed enrichment vs schema) |
|----|--------|---------------------------|-------------|------------------------------------------------|
| …  | …      | …                         | …           | …                                              |
```

ステータスの意味：

- `matched` — seed 行がモックの識別フィールドとメディアペアを保全している
- `seed-enriched` — TUC／ECS／スキーマ向けに行／フィールドを追加したが、Figma 行は残っている
- `figma-suspect` — モック／エクスポートデータが一貫しない、または誤って見える；指摘し、黙って書き換えない
- `schema-blocked` — まだ表現できない；`request-for-refactor`／Open Questions を指す
- `missing` — モックサーフェスが seed されていない（重要なものは `080` でのモック削除を阻害する）

すべてのインベントリモック元が現れるべきである。ギャップと discrepancy は明示する。
手順 `080` は、重要な `missing`／未解決の `schema-blocked` ギャップが残るモックの
削除を拒否する。

## Seed の目的

seed は行を埋める以上のことをすべきである。次に十分にドメインを行使する：

- ローカル開発
- UI 統合
- API テスト
- Playwright ワークフロー
- 検索／フィルタ／ソートの実演
- 状態遷移テスト

該当する場合に含める：

- 複数の代表エンティティ
- 複数のカテゴリ／タイプ
- 現実的な関係
- 異なるライフサイクル状態
- 有効／無効の例
- 下書き／公開／完了／取消の例
- 親子関係
- 多対多関係
- 履歴／版の例
- 空または任意フィールドの例
- テストに有用な境界例
- 検索／フィルタで区別できる値
- 日付／時刻のばらつき
- デモメディア URL
- 画像 URL
- 該当すれば音声／動画 URL
- 該当すればファイル／添付

乱数データより、決定的で読めるデモ値を好む。

テストが予測可能なレコードを必要とする場合、安定した識別子または安定した
ルックアップキーを使う。

本手順で `prisma/schema.prisma` を変更したり黙って再設計したりしてはならない。

成果物：`prisma/seed.ts` と `sop/seed-coverage.md`。

この seed 作業が、既存のバックエンド設計プロンプトまたは既存の `backend/` ツリーに
対するギャップを明らかにしたら、必要な amend ファイルを書く（不要なものは省略）：

1. **Schema** — `schema.prisma` が要件、関係、ライフサイクル状態、制約、履歴ケース、
   または現実的なテストを表現できないとき `prisma/request-for-refactor.md`。
   影響モデル、証拠、seed シナリオ、不十分な理由、重大度（blocking | recommended）、
   最小変更、データ／seed／API／テストへの影響を含める。

2. **Backend** — バックエンド設計プロンプトまたは既存 `backend/` が、それらの発見に
   合わせる API／挙動変更を必要とするとき `sop/Backend amends.md`。

ここで変更を**適用してはならない**。後続の実装がこれらのファイルをマージし、
その後削除する。

## SOP 駆動コミット

**本手順が進むにつれて**コミットする——まとまったスライスごと（成果物の書き出し、
1ルート／機能の抽出、1モックの置換、一部テストが green、…）。手順全体を末尾の
単一コミットに**先送りしてはならない**。

SOP 駆動の件名は `[sop040]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
