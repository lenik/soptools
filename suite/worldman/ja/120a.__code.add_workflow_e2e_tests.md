# ワークフローベースの Playwright テスト実装

## 準備：散在ケースセットのマージとワークフロー改訂

Playwright テスト実装の前に：

1. `sop/` 下の**すべての**サブディレクトリを再帰走査し、散在する作業文書を探す：
   - `TUC.md` — テストユースケース参照集
   - `NTC.md` — 反用例・ネガティブケース
   - `ECS.md` — エッジケースシナリオ
   - `TODO.md` — ライブタスク一覧
2. 各種類を正準ルートファイル `sop/TUC.md`、`sop/NTC.md`、`sop/ECS.md`、
   `sop/TODO.md` へ**マージ**する（重複排除；既存ルートファイルへ折り込み；
   有用な由来見出しを残す）。
3. マージ成功後、散在コピーを**削除**する。
4. **ワークフローへの二次パス（Codex）：** マージ済みケースセットを使い、
   `web-e2e/workflows.md` を改訂する——TUC／NTC／ECS カバレッジが反映されるよう
   ワークフローを追加または調整する；未サポート製品機能を発明しない；
   ワークフロー風疑似コードを保つ（Playwright ソースではない）。

マージ + ワークフロー改訂の後でのみ、以下のテストを実装する。

読む：

- （改訂後の）`web-e2e/workflows.md`
- （マージ後、存在すれば）`sop/TUC.md`
- （マージ後、存在すれば）`sop/NTC.md`
- （マージ後、存在すれば）`sop/ECS.md`

すべてのワークフローをカバーする Playwright テストを実装する。

`sop/` テスト参照を使い、ポジティブケース、ネガティブケース、エッジシナリオが
スキップされないようにする。

コントロールごとの1テストより、ワークフロー指向のテストを好む。

テストは実ユーザー挙動を演習すべきである。

安定したセレクタを使う。

次の順で好む：

- アクセシブルな role/name
- label
- 適切な場合の placeholder
- 安定したセマンティック test ID

次に基づく脆いセレクタを避ける：

- 深い CSS 階層
- nth-child
- 視覚位置
- 生成クラス名

セマンティックセレクタが不十分な場合にのみ `data-testid` を追加する。

Playwright を容易にするためだけに可視 UI を変えない。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop120]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
