# バックエンドの実装

`sop/Backend implementation prompt.md` を確認し、`backend/` 下にバックエンドを実装する。

## Prisma パッケージ

まず既存の `prisma/` ディレクトリを調べる。少なくとも次を期待する：

- `prisma/schema.prisma`
- `prisma/seed.ts`（既に作成済みなら）
- `prisma/package.json`（無ければ追加）

このパッケージを使う。第二の Prisma ルートを発明しない。

## 修正のマージ

シードは、既存のバックエンド設計プロンプトまたは `backend/` ツリーに対するギャップ発見後に
修正要求を残していることがある：

- `prisma/request-for-refactor.md` — スキーマ変更
- `sop/Backend amends.md` — それらの発見が含意するバックエンド／API 変更

実装の**前または同時に**マージする。既知の不十分なスキーマ／API に対して構築しない。

### スキーマ修正のマージ

`prisma/request-for-refactor.md` がある場合：

1. そのファイルのすべての問題を読む。
2. **blocking** 項目を `prisma/schema.prisma`（必要なら `comments.sql` など関連 prisma ファイル）に適用する。
3. **recommended** 項目は、小さく可逆で一貫した API に必要なとき適用する。そうでなければ実装ノートに延期を記す（要求ファイルを残すことでは記さない）。
4. 改訂スキーマに合うよう `prisma/seed.ts` を更新する。
5. 完了したら `prisma/request-for-refactor.md` を**削除**する。

### バックエンド修正のマージ

`sop/Backend amends.md` がある場合：

1. 要求されたすべての API／挙動変更を読む。
2. それらの修正を `backend/` 下の実装に織り込み、マージ済みスキーマ／シードと一貫させる。
3. 修正が衝突する場合は `sop/Backend implementation prompt.md` の設計を調整するのを好む——正しさではシード／スキーマ圧力が勝つ。
4. 完了したら `sop/Backend amends.md` を**削除**する。

## バックエンド

リポジトリが pnpm でインストールおよび実行できるようにする。

`/api/v1/` 下にバックエンド API を実装する。

1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

`CHECKPOINT.md` を参照。
