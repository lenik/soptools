# ワークフローベースの Playwright テストを実装する

## 準備：散在するケース集の統合と workflows の二次加工（Codex）

Playwright テスト実装の前に：

1. `sop/` 配下の**すべての**サブディレクトリを再帰走査し、散在する作業文書を探す：
   - `TUC.md` — テストユースケース参照集
   - `NTC.md` — 反用例・ネガティブケース
   - `ECS.md` — エッジケースシナリオ
   - `TODO.md` — ライブのタスク一覧
2. 種類ごとに **統合**し、ルートの正規ファイル `sop/TUC.md`、`sop/NTC.md`、
   `sop/ECS.md`、`sop/TODO.md` にする（重複除去、既存ルートへ取り込み、出典メモ可）。
3. 統合成功後、散在コピーを**削除**する。
4. **workflows の二次加工（Codex）:** 統合したケース集に基づき
   `web-e2e/workflows.md` を改訂する — TUC / NTC / ECS を反映するよう追加・調整。
   未対応機能を発明しない。ワークフロー風疑似コードのまま（Playwright ソースではない）。

統合と workflows 改訂の後で、以下のテストを実装する。

読む：

- `web-e2e/workflows.md`（改訂後）
- `sop/TUC.md`（統合後、あれば）
- `sop/NTC.md`（統合後、あれば）
- `sop/ECS.md`（統合後、あれば）

全ワークフローを覆う Playwright テストを実装する。

`sop/` のテスト参照を使い、正例・反用例・エッジシナリオを飛ばさないようにする。

コントロールごとのテストより、ワークフロー志向のテストを優先する。

テストは実ユーザー挙動を鍛えること。

安定したセレクタを使う。

次の順で優先する：

- アクセシブルな role/name
- label（ラベル）
- placeholder（適切な場合）
- 安定した意味的 test ID

次に基づく脆いセレクタを避ける：

- 深い CSS 階層
- nth-child
- 視覚位置
- 生成クラス名

意味的セレクタが足りないときだけ `data-testid` を追加する。

Playwright を楽にするためだけに可視 UI を変えない。
