# リポジトリ証拠から PRD を作成する

## 先に WorldMan アーキテクチャを説明する

PRD を書く前に、本モジュールの WorldMan アーキテクチャを説明し、適用すること：

- WorldMan アプリは軽量マイクロサービス的：各アプリは**完全に独立**して動かすことも、対等アプリと**統合**することもできる。
- **独立実行**：基礎データの**簡素なローカル表**を持てる（例：連絡先は氏名／電話のみ）。専用の対等アプリ（連絡先アプリ等）はより完全なモデルを持てる。
- **統合実行**：他アプリのマスタは **cuid2 の不透明参照**のみを保持し、相手 API で解決する。横断 DB 外部キーを既定にしない。
- マスタ主キーは **`cuid(2)`**。独立／統合のどちらでも id を安定に保つ。
- 標準レイアウト：`prisma/`、`backend/`、`web/`、`web-e2e/`、任意の `mobile/` / `mobile-e2e/`、`sop/`、`docs/`、`docker/`、`i-local/`、`i-medium/`、`worldman.json`。
- デプロイ：直接プロセス、Apache/Nginx、またはコンテナ。基準ポート `N` は `wm port -n <name>`（HTTPS = HTTP + 1。bridge の web `80`/`443` を除く。詳細は SOP README）。

PRD は該当箇所で上記制約を反映すること。

## リポジトリ証拠から PRD を出力する

作成または置換する：`sop/PRD.md`。

リポジトリ自体から製品仕様を再構築する。

PRD を書く前に、体系的にリポジトリを検査する。

少なくとも次を確認する（存在する場合）：

- `web/`
- `sop/`
- `docs/`
- `prisma/`
- `README*`
- `package.json`
- `worldman.json`

Web アプリについて次を検査する：

- ルートとページ
- ナビゲーション構造
- ページタイトルとラベル
- フォームとフィールド
- テーブルと列
- ダイアログ、シート、ドロワー、メニュー
- 検索／フィルタ／ソートコントロール
- CRUD 操作
- 一括操作
- 状態／ステータスコントロール
- メディア利用
- mock データ
- フィクスチャ
- 定数／列挙
- ローカルストレージ／セッションストレージの利用
- 検証メッセージ
- 空状態
- エラー状態
- 意図挙動を示すコメント／TODO

偶発的なデザインエクスポート細部をすべて製品要件とみなさない。

繰り返し現れ、意味のある証拠から製品意図を推論する。

## 証拠の優先順位

出典が食い違うときは、次の順で優先する：

1. `sop/` 配下の既存の明示的製品ドキュメント（特に `sop/PRD.md`）、次いで `docs/`
2. 既存の Prisma／ドメイン定義
3. 実装済みのユーザー可視挙動
4. 安定した mock／fixture データ構造
5. 孤立したラベル、プレースホルダ文、または死んだエクスポート／足場コントロール

PRD を「完成して見える」ためだけに要件を発明しない。

重要な要件がリポジトリ証拠から確定できない場合は、**未解決の質問／未解決要件** に記録する。

確認を求めてタスクを止めない。

## PRD 要件

PRD は実装と後続の受入テストに適していること。

証拠が支える範囲で覆う（日本語目次。英語 TOC に依存しない）：

- 製品概要
- 目標
- 範囲
- 範囲外
- 用語
- ユーザー役割
- ドメイン概念
- コアエンティティ
- エンティティ関係
- 業務ルール
- ライフサイクル／状態遷移
- CRUD 挙動
- 検索
- フィルタ
- ソート
- ページネーション（該当時）
- 一括操作
- インポート／エクスポート（該当時）
- メディア
- 履歴／監査（該当時）
- 外部参照
- 検証ルール
- 削除／アーカイブ
- 空状態
- エラー挙動
- 重要な境界事例
- 主な UI ワークフロー
- 非機能要件
- WorldMan 独立実行と統合モデル
- 未解決の質問／未解決要件

実質的な推論要件は、別の開発者が実装またはテストできる程度に明確に書く。

証拠が支えるとき、WorldMan 制約を記録する：

- 本モジュールの独立 vs 統合の動き方
- 所有マスタと、対等モジュールへの不透明 cuid2 参照の区別
- マスタ主キーは `cuid(2)`
- 必要なら `wm port -n <name>` によるデプロイ／ポート期待（HTTPS = HTTP + 1。bridge の `80`/`443` を除く）

文書化する際に既存製品を再設計しない。

証拠またはプロンプトからテスト可能な材料が得られたら、`sop/` 配下も初期化または更新する：

- `TODO.md` — 残りの再構築／実装タスク。状態を最新に保つ
- `TUC.md` — テストユースケース参照集
- `NTC.md` — 反用例・ネガティブケース
- `ECS.md` — エッジケースシナリオ

これらのファイルは後続の e2e ワークフローとツール／サポートクラス作業の入力になる。

完成成果物を直接 `sop/PRD.md` へ書く。
