# バックエンド API テストの追加

自動バックエンド API テストを追加する。

テストは内部実装詳細ではなく、実際の公開 API 挙動をカバーすべきである。

該当する場合、カバーする：

- create
- read
- update
- delete/archive
- list
- search
- filter
- sort
- pagination
- lookup
- relations
- tree operations
- state transitions
- validation failures
- not found
- conflicts
- duplicate prevention
- bulk operations
- history/version behavior
- domain-specific operations

次から発見した重要なエッジケースもテストする：

- `sop/PRD.md`
- 存在すれば `sop/TUC.md`
- 存在すれば `sop/NTC.md`
- 存在すれば `sop/ECS.md`
- `prisma/schema.prisma`
- `prisma/seed.ts`

ユーザープロンプトまたは実装作業が新しいケースを露出したら、速やかに
`sop/TUC.md`、`sop/NTC.md`、`sop/ECS.md` を更新する。
テストは決定的なテストデータを使うべきである。

バックエンドテストを実行する。

バックエンドテストスイートが通るまで、バックエンド実装とテストを直す。

フロントエンド統合問題をフロントエンド問題として扱う前に、バックエンドテストは
通っていなければならない。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop070]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。
