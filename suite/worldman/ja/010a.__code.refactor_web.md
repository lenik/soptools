# Figma 生成 Web アプリケーションの再構成

`web/` 下の Figma エクスポート済み WorldMan UI を監査し、再構成する。

## デザインインベントリ（必須 — 最初に行う）

ファイル分割、ルート移動、ハンドラ改名、アセットのローカライズの
**前に**、後続手順が黙って破壊できないよう Figma ベースラインを記録する。

1. `web/` と、存在すれば `sop/figma-archive/`（手順 `000` が保全）を調べる。
2. 少なくとも次を含む `sop/design-inventory.md` を書く：

```markdown
# Design inventory (Figma baseline)

Captured at step 010 **before** structural refactor. Later steps must not
silently drop entries. Removals require an explicit status + reason here.

## Routes
| path | title / label | source file(s) | status |
|------|---------------|----------------|--------|
| …    | …             | …              | kept   |

## Tabular / tabbed surfaces
| parent route or screen | tab id / label | content summary | status |
|------------------------|----------------|-----------------|--------|
| …                      | …              | …               | kept   |

## Major chrome / navigation
| area | description | status |
|------|-------------|--------|

## Dialogs / sheets / drawers / menus
| name | opened from | status |
|------|-------------|--------|

## Mock / demo data sources
| path or symbol | entities | approx rows / examples | notes |
|----------------|----------|------------------------|-------|

## Typography / fonts (baseline)
| family / stack | weights / styles used | where referenced | status |
|----------------|----------------------|------------------|--------|
| …              | …                    | …                | kept   |

## Color / surface notes (optional but useful for 011)
| role guess (bg/text/accent/…) | sample value or class | notes |
|-------------------------------|----------------------|-------|
```

3. ステータス値：`kept` | `moved:<new path>` | `dropped:<reason>` |
   `dead` / `scaffold`（明らかに非製品のエクスポート chrome のみ）。
4. このファイルが存在し、見つかるナビ可能ルートとタブ／表形式サーフェスを
   すべて列挙するまで、構造編集を**始めてはならない**。

本手順（および後続）の厳格な忠実性ルール：

- 具体的な理由（製品矛盾、重複ルートなど）とともにインベントリを更新せずに、
  列挙済みルートやタブを落としてはならない。
- 「簡略化」「クリーンアップ」「あとで作り直す」は**有効な削除理由ではない**。
- 明らかな Figma 生成欠陥（壊れたレイアウト、ラベル／アクションのない空スタブ）
  を直す場合を除き、既存の視覚デザインと操作モデルを保全する。
- **フォントを変更したり、タイポグラフィ尺度を「アップグレード」したりしてはならない。**
  Figma の `font-family` スタック、ウェイト、サイズを保つ。フォントファイルの
  ローカライズはよいが、Inter / system-ui / テーマパックのディスプレイ書体への
  差し替えは不可。

その後、現在のアプリを調べ、次を特定する：

- ルートとページ
- 大きな TSX ファイル
- ページレベルコンポーネント
- 共有コンポーネント
- ダイアログ、シート、ドロワー、ポップオーバー
- フォーム
- テーブルとリスト
- 検索、フィルタ、ソート挙動
- メニューとコンテキストメニュー
- CRUD 操作
- ローカル／モックデータ元
- ローカル永続化
- インタラクティブコントロール
- 未完成または死んだコントロール

有用なら構造を再構成する。

## Figma デモアセットのローカライズ

Figma Make プロトタイプはしばしばリモートデモメディア（画像、フォント、音声、
動画、Lottie など）をホットリンクする。本再構成では UI を自己完結にする：

1. `web/` を走査し、デモアセットとして使われる絶対 `http(s)://` URL を探す（CSS
   `@import` / `@font-face`、`<img>` / `<audio>` / `<video>`、背景 URL、
   メディアの fetch/import など）。
2. 各アセットを**そのまま** `web/assets/` 下にダウンロードする。有用なら種類で
   グループ化する：
   ```text
   web/assets/
       images/
       fonts/
       audio/
       video/
       …
   ```
   ダウンロード時、Google / Google Fonts / gstatic、Facebook /
   fbcdn などのホストは**必ず**ローカル HTTP プロキシ `http://localhost:8118`
   を使う（`http_proxy` / `https_proxy`、または curl/wget `--proxy` 経由）。
   それらのホストへの長時間の直結取得を試みてはならない。他の CDN はまず直結を試し、
   失敗したらプロキシ経由で再試行し、実ファイルを得るまで続ける。諦めて偽アセットに
   置き換えてはならない。
3. すべての参照をローカルパスまたはモジュール import に書き換える。安定した説明的な
   ファイル名を好む。アセットに付いていたライセンス／帰属注記は残す。
4. **フォント**については、実際の `@font-face` ファイルをダウンロードし、CSS で
   **同じファミリー名、ウェイト、スタイル**を保つ。「一貫性のため」やテーマパックの
   好みだからといって別書体に置き換えてはならない。パスが変わってもファミリーが
   同じなら、`sop/design-inventory.md` → Typography を更新する。
5. コミットするソースにデモ CDN／ストックメディアのホットリンクを残さない。
   非アセットの API エンドポイントと意図的な第三者連携はスキップする。

**ライセンスと真正性（重要）：** Figma プロトタイプに付くホットリンクは、通常きわめて
緩い条件を持つ。例えば Unsplash 写真は
[Unsplash License](https://unsplash.com/license) を使う：個人・商用ともに無料、
支払い不要、撮影者の許可不要、帰属表示も不要（
[ここ](https://www.zhihu.com/question/50969084) でも議論されている）。これは開発と
プロトタイプ検証に特に友好的である。本アプリはストック写真ギャラリーではなく、
そのようなサービスとも競合しない。**ライセンス制約を過度に解釈してはならない。**
ダウンロードを飛ばしたり、実メディアをプレースホルダ、単色ブロック、偽画像、その他の
代替物で置き換えたりしてはならない——実際のリモートアセットを `web/assets/` に保存する。

## ページ抽出

適切なら、大きな／モノリシックな TSX からルートレベルのページを抽出する。

責務に基づく構造を好む：

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

### ディレクトリの役割（Vite + React — Next.js ではない）

| ディレクトリ | 役割 |
|-----------|------|
| `pages/` | **ルート境界** — ナビ可能な画面ごとのエントリモジュール（ルーター＋ route-smoke 列挙） |
| `features/` | ページ固有の UI・状態・ドメイン塊 |
| `components/` | ルート／機能横断で共有する再利用 UI |

ルール：

- 薄い `pages/FooPage.tsx` 再エクスポートは、実ページ本体が `features/` 下にある場合
  **のみ**許可する（例：`features/foo/…`）。
- 完全なページ実装を `components/` に置き、`pages/` をその空の再エクスポートにしては
  **ならない**。
- タブを含むモノリシック画面を分割するとき、**すべての**タブを到達可能に保つ。
  内部タブ付きの1ルート、またはタブごとの子ルートを好む——いずれにせよ
  `sop/design-inventory.md` を更新する。ファイルが「長すぎる」からといってタブ内容を
  削除してはならない。

過大なファイルは**必ず**分割する。長すぎるファイルは通常、構造が誤っている：
services、discovery などの分散が欠けている、および／または専用の外部ソースファイルへ
抽出すべきツール／サポートコードがある。

次に従って分割する：

- ルート境界
- 機能境界
- 状態の所有権
- 再利用 UI の責務
- ドメイン操作
- 共有 services／discovery／ツールサポートを専用モジュールへ抽出

構造変更が必要でない限り、既存の視覚デザインと操作モデルを保全する。

## UI テスト容易性の再構成

自動化テストと保守を容易にするため、UI ロジックを再構成する。

ビジネスロジックを匿名 JSX コールバック内に直接置いてはならない。

匿名コールバックが許されるのは次のみ：

- 引数の転送
- イベント値の抽出
- イベントを名前付きハンドラ呼び出しへ適応

悪い例：

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

好ましい例：

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

イベントベースの挙動では、実用的な範囲でイベント抽出とイベント非依存の挙動を分ける。

例：

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

次のような明確な命名を使う：

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

意味のあるセマンティック名がない場合を除き、`button1_click` のように視覚位置に
不必要に結びついた名前を避ける。

## ルート `package.json` スクリプト（必須）

**リポジトリルート**を pnpm workspace 親とし、共通スクリプト目標を備える。作成
または更新：

- `pnpm-workspace.yaml` — 少なくとも `.`、`web`、`backend`、`prisma`、
  `web-e2e`（`mobile` / `mobile-e2e` が実パッケージになったら追加）
- ルート `package.json` — `private: true`；`dev` が分流するなら `concurrently` を
  `devDependency` に；および下表のスクリプト

`web/package.json` だけでは不十分。後続手順と運用はリポジトリルートから実行する
（`pnpm dev`、`pnpm db:migrate`、`pnpm e2e`）。

### 必須のルートスクリプト

| スクリプト | 転送先 | 目的 |
|------------|--------|------|
| `dev` | `concurrently -kic blue,green npm:dev:*` | 全 `dev:*` をまとめて実行 |
| `dev:web` | `pnpm -C web dev` | Vite（または同等）web |
| `dev:backend` | `pnpm -C backend dev` | API プロセス |
| `db:generate` | `pnpm -C prisma generate` | `prisma generate`（および post-link フック） |
| `db:migrate` | `pnpm -C prisma migrate` | **`prisma migrate deploy`** — 既存移行を適用（CI / 本番 / 共有 DB） |
| `db:migrate:dev` | `pnpm -C prisma migrate:dev` | **`prisma migrate dev`** — ローカル開発で作成＋適用 |
| `db:push` | `pnpm -C prisma db:push` | 使う場合の `prisma db push` |
| `db:seed` | `pnpm -C prisma seed` | Seed |
| `db:studio` | `pnpm -C prisma studio` | Studio |
| `e2e` | `pnpm -C web-e2e test` | Playwright（あれば `:smoke` / `:report` も） |

後続任意（パッケージがあるとき）：`mobile`、`mobile:*`、`e2e:smoke`、…

### 命名規則（重複を作らない）

- リポジトリルートの DB 作業は **`db:*`** 前置に統一。ルートに
  `prisma:generate` / `prisma:migrate` を**併存させない**——`db:*` と同コマンドの別名。
- **`db:migrate` と `db:migrate:dev` は両方残す**——**同じではない**：
  - `db:migrate` → `migrate deploy`（非対話適用）
  - `db:migrate:dev` → `migrate dev`（対話的作成）
- `db:migrate` を繰り返すだけの第三別名（例 `db:deploy`）を**追加しない**。
- `prisma/package.json` 内はルートが転送する短名：`generate`、`migrate`（= deploy）、
  `migrate:dev`、`db:push`、`seed`、`studio`。`prisma/package.json` を初めて足すとき
  （手順 `030` / `060`）に揃える。本手順では少なくともルートスクリプトを先に配線する。
- `backend/package.json` はローカル DX で `../prisma` を呼んでよい。正規の運用入口は
  ルートの `pnpm db:*`。

ルート `package.json` が既にある（再実行／半完成ツリー）場合はこれらのスクリプトを
**マージ**し、無関係なものを消さない。古いルート `prisma:*` 別名は `db:*` に改名する。

## プロジェクト `sop/` ワークスペース

本再構成および後続の複雑な構築手順では、`sop/` 下に作業文書を維持する：

- `sop/TODO.md` を生きたタスク一覧とし、作業の進行に合わせて項目状態を更新する。
- 構造を意図的に動かすときは `sop/design-inventory.md` を最新に保つ。
- ユーザーが複雑なプロンプトを渡したら、候補テストを速やかに抽出または構成して：
  - `sop/TUC.md` — テストユースケース参照集
  - `sop/NTC.md` — 反用例／ネガティブケース
  - `sop/ECS.md` — エッジケースシナリオ
- 製品要件は `sop/PRD.md`（PRD 手順で執筆）。
- 共有ツール／サポートクラスの抽出や後続 e2e カバレッジ執筆では、これらの
  `sop/` 文書を優先する。

明らかな Figma 生成欠陥の修正を除き、本段階で製品挙動を変えてはならない。

## SOP 駆動コミット

**本手順が進むにつれて**コミットする——まとまったスライスごと（成果物の書き出し、
1ルート／機能の抽出、1モックの置換、一部テストが green、…）。手順全体を末尾の
単一コミットに**先送りしてはならない**。

SOP 駆動の件名は `[sop010]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。

`011` のテーミングが `extend: previous` で本手順にマージされる場合も、それらの
コミットには `[sop010]` を使い続ける（グラフ上は1手順）。
