# Figma 生成 Web アプリケーションの再構成

`web/` 下の Figma エクスポート済み WorldMan UI を監査し、再構成する。

## デザインインベントリ（必須 — 最初に行う）

ファイル分割、ルート移動、ハンドラ改名、アセットのローカライズの
**前に**、後続手順が黙って破壊できないよう Figma ベースラインを記録する。

1. `web/` と、存在すれば `sop/figma-archive/`（手順 `000` が保全）を調べる。
2. 少なくとも次を含む `sop/design-inventory.md` を書く：

```markdown
# Design inventory (Figma baseline)

Captured at step 010 **before** structural refactor. Later steps must not
silently drop entries. Removals require an explicit status + reason here.

## Routes
| path | title / label | source file(s) | status |
|------|---------------|----------------|--------|
| …    | …             | …              | kept   |

## Tabular / tabbed surfaces
| parent route or screen | tab id / label | content summary | status |
|------------------------|----------------|-----------------|--------|
| …                      | …              | …               | kept   |

## Major chrome / navigation
| area | description | status |
|------|-------------|--------|

## Dialogs / sheets / drawers / menus
| name | opened from | status |
|------|-------------|--------|

## Mock / demo data sources
| path or symbol | entities | approx rows / examples | notes |
|----------------|----------|------------------------|-------|
```

3. ステータス値：`kept` | `moved:<new path>` | `dropped:<reason>` |
   `dead` / `scaffold`（明らかに非製品のエクスポート chrome のみ）。
4. このファイルが存在し、見つかるナビ可能ルートとタブ／表形式サーフェスを
   すべて列挙するまで、構造編集を**始めてはならない**。

本手順（および後続）の厳格な忠実性ルール：

- 具体的な理由（製品矛盾、重複ルートなど）とともにインベントリを更新せずに、
  列挙済みルートやタブを落としてはならない。
- 「簡略化」「クリーンアップ」「あとで作り直す」は**有効な削除理由ではない**。
- 明らかな Figma 生成欠陥（壊れたレイアウト、ラベル／アクションのない空スタブ）
  を直す場合を除き、既存の視覚デザインと操作モデルを保全する。

その後、現在のアプリを調べ、次を特定する：

- ルートとページ
- 大きな TSX ファイル
- ページレベルコンポーネント
- 共有コンポーネント
- ダイアログ、シート、ドロワー、ポップオーバー
- フォーム
- テーブルとリスト
- 検索、フィルタ、ソート挙動
- メニューとコンテキストメニュー
- CRUD 操作
- ローカル／モックデータ元
- ローカル永続化
- インタラクティブコントロール
- 未完成または死んだコントロール

有用なら構造を再構成する。

## Figma デモアセットのローカライズ

Figma Make プロトタイプはしばしばリモートデモメディア（画像、フォント、音声、
動画、Lottie など）をホットリンクする。本再構成では UI を自己完結にする：

1. `web/` を走査し、デモアセットとして使われる絶対 `http(s)://` URL を探す（CSS
   `@import` / `@font-face`、`<img>` / `<audio>` / `<video>`、背景 URL、
   メディアの fetch/import など）。
2. 各アセットを**そのまま** `web/assets/` 下にダウンロードし、有用なら種類で
   グループ化する：
   ```text
   web/assets/
       images/
       fonts/
       audio/
       video/
       …
   ```
   ダウンロード時、Google／Google Fonts／gstatic、Facebook／fbcdn などのホストは
   **必ず**ローカル HTTP プロキシ `http://localhost:8118` を使う
   （`http_proxy` / `https_proxy`、または curl/wget `--proxy`）。それらのホストへの
   長い直接取得を試みない。他の CDN はまず直接試し、失敗したら実ファイルが
   取れるまでプロキシ経由で再試行する。諦めて偽アセットに置き換えない。
3. すべての参照をローカルパスまたはモジュール import に書き換える。安定で
   説明的なファイル名を好み、アセットに付いていたライセンス／帰属注記を残す。
4. コミットするソースにデモ CDN／ストックメディアのホットリンクを残さない。
   非アセット API エンドポイントと意図的な第三者統合はスキップする。

**ライセンスと真正性（重要）：** Figma プロトタイプに供給されるホットリンクは
通常非常に寛容な条件を持つ。例えば Unsplash 写真は
[Unsplash License](https://unsplash.com/license) を使い：個人・商用とも無料、
支払い不要、撮影者許可不要、帰属も不要（
[ここ](https://www.zhihu.com/question/50969084)でも議論）。これは開発と
プロトタイプ試験に特に友好的。本アプリはストックフォトギャラリー基盤ではなく、
そうしたサービスと競合しない。**ライセンス制約を過度に解釈しない。**
ダウンロードをスキップしたり、実メディアをプレースホルダ、単色ブロック、
偽画像、その他の代替に置き換えたりしない——実際のリモートアセットを
`web/assets/` に保存する。

## ページ抽出

適切なら、大きく／モノリシックな TSX からルートレベルのページを抽出する。

責任に基づく構造を好む：

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

### ディレクトリの役割（Vite + React — Next.js ではない）

| ディレクトリ | 役割 |
|-----------|------|
| `pages/` | **ルート境界** — ナビ可能な画面ごとのエントリモジュール（ルーター + route-smoke 列挙） |
| `features/` | ページ固有の UI・状態・ドメイン塊 |
| `components/` | ルート／機能横断で共有する再利用 UI |

ルール：

- 薄い `pages/FooPage.tsx` 再エクスポートは、実ページ本体が `features/` 下
  （例：`features/foo/…`）にある場合**のみ**許可する。
- 完全なページ実装を `components/` に置き、`pages/` をその空の再エクスポートに
  しては**ならない**。
- タブを含むモノリシック画面を分割するとき、**すべての**タブを到達可能に保つ。
  内部タブ付きの1ルート、またはタブごとの子ルートのどちらかを好み——いずれにせよ
  `sop/design-inventory.md` を更新する。ファイルが「長すぎる」という理由で
  タブ内容を削除してはならない。

過大なファイルは**必ず**分割する。長すぎるファイルは通常、構造が誤り：
サービス、ディスカバリなどの分散が欠けている、および／または専用の外部ソースへ
抽出すべきツール／サポートコードがある。

次に従って分割する：

- ルート境界
- 機能境界
- 状態の所有権
- 再利用 UI の責任
- ドメイン操作
- 共有サービス／ディスカバリ／ツールサポートを専用モジュールへ抽出

構造変更が必要な場合を除き、既存の視覚デザインと操作モデルを保全する。

## UI テスト容易性の再構成

自動テストと保守を容易にするよう UI ロジックを再構成する。

ビジネスロジックを匿名 JSX コールバック内に直接置いてはならない。

匿名コールバックが許されるのは：

- 引数の転送
- イベント値の抽出
- イベントを名前付きハンドラ呼び出しへ適応

悪い例：

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

好ましい例：

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

イベントベースの挙動では、実用的ならイベント抽出とイベント非依存の挙動を分ける。

例：

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

明確な命名を使う：

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

意味のあるセマンティック名がない場合を除き、`button1_click` のような視覚位置に
不必要に結びついた名前を避ける。

## プロジェクト `sop/` ワークスペース

本再構成および後続の複雑な構築手順では、`sop/` 下に作業文書を維持する：

- `sop/TODO.md` をライブタスク一覧として保ち、進行に合わせて項目状態を更新する。
- 構造を意図的に動かすとき、`sop/design-inventory.md` を最新に保つ。
- ユーザーが複雑なプロンプトを渡したら、候補テストを速やかに抽出または構成して：
  - `sop/TUC.md` — テストユースケース参照集
  - `sop/NTC.md` — 反用例・ネガティブケース
  - `sop/ECS.md` — エッジケースシナリオ
- 製品要件は `sop/PRD.md`（PRD 手順で作成）。
- 共有ツール／サポートクラスの抽出や後続 e2e カバレッジ作成では、これらの `sop/` 文書を好む。

明らかな Figma 生成欠陥を直す場合を除き、本段階で製品挙動を変えない。

## SOP 駆動コミット

本手順が**進むにつれて**コミットする——まとまったスライスのあと（成果物の書き出し、
1ルート／機能の抽出、1モック置換、一部テストが green、…）。
手順全体を末尾の単一コミットに**先送りしない**。

SOP 駆動の件名は `[sop010]` で始めなければならない。本 SOP パックの
`CHECKPOINT.md` を参照。

`011` テーミングが `extend: previous` で本手順にマージされる場合も、それらの
コミットに `[sop010]` を使い続ける（グラフ上は1手順）。
