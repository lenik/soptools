# リポジトリ根拠でバックエンド実装を準備する

これは、通常バックエンド実装プロンプトを生成する GPT 手順の Codex フォールバックである。

すでにリポジトリ内で作業しているため、再び Codex に貼り付けるためのプロンプトを生成しない。

代わりにリポジトリを検査し、具体的な実装計画を用意してから、バックエンド実装手順に入れる状態にする。

少なくとも次を確認する：

- `sop/PRD.md`
- `sop/TUC.md`（あれば）
- `sop/NTC.md`（あれば）
- `sop/ECS.md`（あれば）
- `sop/TODO.md`（あれば）
- `prisma/schema.prisma`
- `prisma/seed.ts`
- `web/`
- `package.json`
- `pnpm-workspace.yaml`
- 既存 `backend/`

併せて検査する：

- Web ルート
- フロントエンドのデータ／サービス抽象
- mock データ
- 既存のリクエスト／レスポンス形状
- ドメイン列挙と状態遷移
- 検索／フィルタ／ソート挙動
- 一括操作
- エンティティ横断ナビゲーション
- 現行 UI を超えて再利用できそうな機能

共有ツールやサポートクラスを抽出するときは、すでに `sop/` に記録された要件とシナリオ（`PRD.md`、`TUC.md`、`NTC.md`、`ECS.md`）を優先する。

計画項目の完了または延期に合わせて、`sop/TODO.md` の状態を最新に保つ。
作成する：`docs/backend-implementation-plan.md`。

## バックエンド前提

対象：

- `pnpm`
- Node.js
- TypeScript

API プレフィックス：`/api/v1/`

バックエンドは、現行 Web UI に必要な最小エンドポイントだけでなく、有用なドメイン能力を公開すること。

各ドメインリソースについて、次が意味のある必要かを評価する：

- CRUD
- 一覧
- 詳細
- 検索
- ルックアップ
- オートコンプリート
- フィルタ
- ソート
- ページネーション
- 一括取得
- 一括作成／更新／削除
- リレーション走査
- ツリー走査
- 状態遷移
- 履歴
- バージョンアクセス
- 検証
- 統計
- 集計
- インポート
- エクスポート
- メディア操作
- 外部参照の解決

全モデルに機械的に全能力を規定しない。

計画は次を定義する：

- バックエンドアーキテクチャ
- ドメイン／サービス境界
- ルートグループ
- 検証戦略
- エラーモデル
- シリアライズ規約
- ページネーション規約
- フィルタ／ソート規約
- リソース能力
- ドメイン固有操作
- 一括操作セマンティクス
- テスト戦略
- web/ との統合上の論点
- 実装順

次の分離を優先する：

- ルート／コントローラ層
- 検証
- サービス／ドメイン論理
- データアクセス
- 共有エラー
- API シリアライズ

ドメイン論理をルートハンドラへ直接置かない。

## リポジトリ根拠のギャップ処理

`sop/PRD.md`、`schema.prisma`、シードデータ、Web アプリが食い違う場合：

- 矛盾を `docs/backend-implementation-plan.md` に記録する
- どの出典が権威に見えるかとその理由を示す
- 最小で可逆な実装仮定を選ぶ
- スキーマや製品を黙って再設計しない

`prisma/request-for-refactor.md` があれば確認し、関連する blocking 項目を実装計画に取り込む。スキーマ変更は後続の **バックエンド実装** 手順（`060`）で `prisma/schema.prisma` へマージする。

このファイルを呼び出すワークフローが計画と実装の結合を明示的に求めない限り、この手順ではバックエンドを実装しない。
