# 集成 web 与后端

连接 `web/` 与 `backend/`，使 UI 使用真实 API。

## 目标

- 在合适处用后端 API 替换 demo、mock 与仅本地数据源。
- 保持已批准的 UI 结构与视觉设计。不要只因集成进行中就重设计应用。
- 引入清晰的前端 API/服务层（优先 `web/src/services/` 或等价客户端模块）。避免在页面组件里散落裸 `fetch()`。
- 复核 `sop/design-inventory.md`：每个 `kept`/`moved` 路由与页签在集成后仍须渲染其主要内容（不能因 seed/API 为空而永久空白表）。

## Seed 覆盖门控（删除 mock 之前）

1. 读 `sop/seed-coverage.md`（缺失则按 `040` 规则创建/更新），含 **差异记录**。
2. 对每个供给用户可见列表/表格/详情的 mock 来源：
   - 确认在 `prisma db seed`（或项目的 seed 命令）之后，API + seed 能返回等价的代表性行（名称、数量、媒体、状态）。
   - 确认 **media ↔ text** 配对仍与 Figma mock 所示一致（没有海报/标题互换）。`mismatched` 行须先修复，或在删除 mock 前写明差异条目。
   - 关键面上的 `missing` 或未解决的 `schema-blocked` 视为门控失败。`figma-suspect` 仅在有记录理由时可继续；`seed-enriched` 在原始 Figma 行仍在时可以。
   - 若仍有**关键缺口**，先修 `prisma/seed.ts` / 后端，或为该面保留临时本地回退，并记在 `sop/TODO.md` + `seed-coverage.md`。
3. **不要**删掉 mock 却让先前展示 Figma demo 数据的面变成空 UI。

仅当某来源通过门控后，才用 API 替换该来源。

## UI 行为

确保 UI 正确处理这些情况：

- loading
- empty state（仅当领域真正为空——不是 seed 滞后）
- server error
- validation error
- not found
- conflict
- save success
- delete/archive confirmation
- refresh
- reload persistence
- search
- filter
- sort
- pagination

对大或可复用的数据集，在符合领域时优先服务端行为。

## 当集成暴露后端问题时

若集成暴露真实的后端设计问题，按需重构后端。后端行为变更时：

- 更新后端测试
- 保持公共 API 一致
- 重新运行后端测试

## SOP 驱动的提交

**随本步骤演进**提交——每完成一块连贯切片（产物已写出、某条路由/功能已抽出、某个 mock 已替换、某子集测试已绿等）。**不要**把整步工作拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop080]` 开头。见本 SOP 包中的 `CHECKPOINT.md`。
