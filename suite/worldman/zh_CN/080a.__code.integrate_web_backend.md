# 将 web 与后端集成

连接 `web/` 与 `backend/`，使 UI 使用真实 API。

## 目标

- 在合适处用后端 API 替换 demo、mock 与仅本地数据源。
- 保持已批准的 UI 结构与视觉设计。不要仅仅因为集成进行中就重设计应用。
- 引入清晰的前端 API/service 层（偏好 `web/src/services/` 或等价客户端模块）。避免在页面组件中散落原始 `fetch()` 调用。
- 复核 `sop/design-inventory.md`：每个 `kept`/`moved` 路由与页签在集成后仍须渲染其主要内容（不能因为 seed/API 为空而永久空白表）。

## Seed 覆盖门控（删除 mock 之前）

1. 阅读 `sop/seed-coverage.md`（若缺失则按 `040` 规则创建/更新）。
2. 对每个向用户可见列表/表格/详情供数的 mock 来源：
   - 确认在 `prisma db seed`（或项目的 seed 命令）之后，API + seed 能返回等价代表性行（名称、
     数量、媒体、状态）。
   - 若仍有**关键缺口**，先修 `prisma/seed.ts` / 后端，
     或为该面保留临时本地回退，并记在
     `sop/TODO.md` + `seed-coverage.md`。
3. **不要**删除 mock 却让先前展示 Figma demo 数据的面变成空 UI。

仅当某来源的门控通过后，才用 API 替换该来源。

## UI 行为

确保 UI 正确处理这些情形：

- loading
- empty state（仅当领域确实为空——不是 seed 滞后）
- server error
- validation error
- not found
- conflict
- save success
- delete/archive confirmation
- refresh
- reload persistence
- search
- filter
- sort
- pagination

当适合领域时，对大型或可复用数据集偏好服务端行为。

## 当集成暴露后端问题时

若集成暴露真实后端设计问题，按需重构后端。当后端行为变更时：

- 更新后端测试
- 保持公共 API 一致
- 重新运行后端测试

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop080]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
