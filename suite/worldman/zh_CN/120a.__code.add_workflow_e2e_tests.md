# 实现基于工作流的 Playwright 测试

## 准备：合并散落用例集并修订工作流

实现 Playwright 测试之前：

1. 递归扫描 `sop/` 下**所有**子目录中的散落工作文档：
   - `TUC.md` — 测试用例参考集
   - `NTC.md` — 反用例 / 负面测试用例
   - `ECS.md` — 边界场景
   - `TODO.md` — 活任务清单
2. 将每种**合并**到规范根文件 `sop/TUC.md`、
   `sop/NTC.md`、`sop/ECS.md` 与 `sop/TODO.md`（去重；折入任何既有根文件；
   保留有用出处标题）。
3. 合并成功后**删除**散落副本。
4. **工作流二次通过（Codex）：** 使用合并后的用例集，修订
   `web-e2e/workflows.md` — 增改工作流以反映 TUC / NTC / ECS 覆盖；
   不要发明不支持的产品功能；保持工作流风格伪代码（不是 Playwright 源码）。

仅在合并 + 工作流修订之后，再实现下方测试。

阅读：

- `web-e2e/workflows.md`（修订后）
- `sop/TUC.md`（合并后，若存在）
- `sop/NTC.md`（合并后，若存在）
- `sop/ECS.md`（合并后，若存在）

实现覆盖所有工作流的 Playwright 测试。

使用 `sop/` 测试参考，确保正例、反例与边界场景不被跳过。

偏好面向工作流的测试，而非每个控件一个测试。

测试应锻炼真实用户行为。

使用稳定选择器。

按此顺序偏好：

- 可访问角色/名称
- label
- 适当时的 placeholder
- 稳定语义 test ID

避免基于以下内容的脆弱选择器：

- 深层 CSS 层级
- nth-child
- 视觉位置
- 生成的类名

仅在语义选择器不足时添加 `data-testid`。

不要仅为让 Playwright 更容易而改动可见 UI。

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop120]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
