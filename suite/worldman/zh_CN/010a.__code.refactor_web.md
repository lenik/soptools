# 重构 Figma 生成的 web 应用

审计并重构 `web/` 下由 Figma 导出的 WorldMan UI。

## 设计清单（必需 — 先做这件事）

在拆分文件、移动路由、重命名处理器或本地化
资源**之前**，先固化 Figma 基线，以免后续步骤静默毁掉它。

1. 检查 `web/`，以及若存在则检查 `sop/figma-archive/`（由步骤
   `000` 保留）。
2. 写出 `sop/design-inventory.md`，至少包含：

```markdown
# Design inventory (Figma baseline)

Captured at step 010 **before** structural refactor. Later steps must not
silently drop entries. Removals require an explicit status + reason here.

## Routes
| path | title / label | source file(s) | status |
|------|---------------|----------------|--------|
| …    | …             | …              | kept   |

## Tabular / tabbed surfaces
| parent route or screen | tab id / label | content summary | status |
|------------------------|----------------|-----------------|--------|
| …                      | …              | …               | kept   |

## Major chrome / navigation
| area | description | status |
|------|-------------|--------|

## Dialogs / sheets / drawers / menus
| name | opened from | status |
|------|-------------|--------|

## Mock / demo data sources
| path or symbol | entities | approx rows / examples | notes |
|----------------|----------|------------------------|-------|

## Typography / fonts (baseline)
| family / stack | weights / styles used | where referenced | status |
|----------------|----------------------|------------------|--------|
| …              | …                    | …                | kept   |

## Color / surface notes (optional but useful for 011)
| role guess (bg/text/accent/…) | sample value or class | notes |
|-------------------------------|----------------------|-------|
```

3. 状态取值：`kept` | `moved:<new path>` | `dropped:<reason>` |
   `dead` / `scaffold`（仅用于明显非产品的导出 chrome）。
4. 在该文件存在且列出你能找到的每条可导航路由与每个页签/表格面
   之前，**不要**开始结构编辑。

本步骤其余部分（以及后续步骤）的硬性保真规则：

- 不得在未用具体理由更新清单的情况下丢弃已列出的路由或页签
  （产品矛盾、重复路由等）。
- “简化”“清理”或“以后再重建”**不是**有效的丢弃理由。
- 除非修复明显的 Figma 生成缺陷（坏布局、无标签/无动作的空桩控件），
  否则保持既有视觉设计与交互模型。
- **不要更改字体或“升级”字号阶梯。** 保留 Figma 的
  `font-family` 栈、字重与字号。本地化字体文件可以；
  换成 Inter / system-ui / 主题包展示字体则不可以。

然后检查当前应用并识别：

- 路由与页面
- 大型 TSX 文件
- 页面级组件
- 共享组件
- 对话框、sheet、drawer 与 popover
- 表单
- 表格与列表
- 搜索、筛选与排序行为
- 菜单与上下文菜单
- CRUD 操作
- 本地/mock 数据源
- 本地持久化
- 交互控件
- 不完整或死控件

然后在有用处重构结构。

## 本地化 Figma demo 资源

Figma Make 原型常热链远程 demo 媒体（图片、字体、音频、
视频、Lottie 等）。在本重构中，使 UI 自包含：

1. 扫描 `web/` 中用作 demo 资源的绝对 `http(s)://` URL（CSS
   `@import` / `@font-face`、`<img>` / `<audio>` / `<video>`、背景
   URL、媒体的 fetch/import 等）。
2. 将每个资源**原样**下载到 `web/assets/`，按种类分组（有用时）：
   ```text
   web/assets/
       images/
       fonts/
       audio/
       video/
       …
   ```
   下载时，Google / Google Fonts / gstatic、Facebook /
   fbcdn 等主机**必须**使用本地 HTTP 代理 `http://localhost:8118`
   （通过 `http_proxy` / `https_proxy`，或 curl/wget `--proxy`）。不要尝试
   对这些主机做长时间直连。对其它 CDN，先试直连；若
   失败，经代理重试直至拿到真实文件。不要
   放弃或用假资源替代。
3. 把每处引用改写为本地路径或模块导入。偏好稳定、
   描述性文件名；保留随资源附带的任何许可或署名说明。
4. 对**字体**：下载真实的 `@font-face` 文件，并在 CSS 中保持**相同的
   族名、字重与样式**。不要为了“一致性”或因为主题包偏好而换成
   另一种字体。若路径变更但族名不变，更新
   `sop/design-inventory.md` → Typography。
5. 提交源码中不要留下 demo CDN / 库存媒体热链。跳过
   非资源 API 端点与有意的第三方集成。

**许可与真实性（重要）：** Figma 原型中提供的热链通常带有非常宽松的
条款。例如 Unsplash 照片使用
[Unsplash License](https://unsplash.com/license)：可免费用于个人与
商业用途，无需付费、无需摄影师许可、无需署名
（亦有讨论见
[此处](https://www.zhihu.com/question/50969084)）。这对开发与原型测试
尤其友好。本应用不是图库平台，也不与此类服务竞争。**不要过度解读
许可约束。** 不要跳过下载，也不要用占位符、纯色块、假图或其它
替代品替换真实媒体——把实际远程资源保存到 `web/assets/`。

## 页面抽取

在合适时，从大型或单体 TSX 文件中抽取路由级页面。

按职责偏好如下结构：

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

### 目录职责（Vite + React — 非 Next.js）

| 目录 | 职责 |
|------|------|
| `pages/` | **路由边界** — 每个可导航屏面对应一个入口模块（路由器 + 路由冒烟枚举） |
| `features/` | 页面专属 UI、状态与领域分块 |
| `components/` | 跨路由/功能共享的可复用 UI |

规则：

- 仅当真实页面主体位于 `features/` 下时（如 `features/foo/…`），才允许
  薄的 `pages/FooPage.tsx` 再导出。
- **不要**把完整页面实现停在 `components/` 下，却让
  `pages/` 只剩对这些组件的空再导出。
- 拆分含页签的单体屏幕时，保持**所有**页签可达。偏好一条带内部页签的
  路由，或每个页签一条子路由——无论哪种都更新
  `sop/design-inventory.md`。绝不要因为文件“太长”就删除页签内容。

过大文件**必须**拆分。文件过长通常意味着结构不对：缺少通过
services、discovery 等机制的去中心化，和/或应抽到专用外部源文件的
工具/支撑代码。

按以下边界拆分：

- 路由边界
- 功能边界
- 状态所有权
- 可复用 UI 职责
- 领域操作
- 共享 services / discovery / 工具支撑抽到专用模块

除非结构变更必要，否则保持既有视觉设计与交互模型。

## UI 可测试性重构

重构 UI 逻辑，使自动化测试与维护更容易。

业务逻辑不得直接写在匿名 JSX 回调里。

匿名回调仅可：

- 转发参数
- 提取事件值
- 把事件适配为命名处理器调用

不良：

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

优选：

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

对基于事件的行为，在可行时把事件提取与事件无关行为分开。

示例：

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

使用清晰命名，例如：

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

除非没有有意义的语义名，避免不必要地绑定视觉位置的名字如 `button1_click`。

## 项目 `sop/` 工作区

在本重构及后续复杂构建步骤中，于 `sop/` 下维护工作文档：

- 将 `sop/TODO.md` 作为活任务清单；随工作推进更新条目状态。
- 有意移动结构时保持 `sop/design-inventory.md` 最新。
- 当用户给出复杂提示时，尽快把候选测试提取或构造进：
  - `sop/TUC.md` — 测试用例参考集
  - `sop/NTC.md` — 反用例 / 负面测试用例
  - `sop/ECS.md` — 边界场景
- 产品需求位于 `sop/PRD.md`（在 PRD 步骤中撰写）。
- 抽取共享工具/支撑类以及撰写后续 e2e 覆盖时，优先使用这些 `sop/` 文档。

本阶段除非修复明显的 Figma 生成缺陷，否则不要改变产品行为。
