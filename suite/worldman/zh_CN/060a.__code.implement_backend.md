# 实现后端

检出 `sop/Backend implementation prompt.md`，并在 `backend/` 下实现后端。

## Prisma 包

先检查既有 `prisma/` 目录。至少期望：

- `prisma/schema.prisma`
- `prisma/seed.ts`（若已撰写）
- `prisma/package.json`（缺失则添加）

使用此包；不要发明第二个 Prisma 根。

`prisma/package.json` 脚本应与根上 `db:*` 转发目标一致（见步骤 `010`）：`generate`、`migrate`（= `prisma migrate deploy`）、`migrate:dev`、`db:push`、`seed`、`studio`。不要再引入根上的 `prisma:generate` 别名——使用 `pnpm db:generate` / `pnpm db:migrate` / `pnpm db:migrate:dev`。

## 修订合并

Seed 在发现相对既有后端设计提示或 `backend/` 树的缺口后，可能留下修订请求：

- `prisma/request-for-refactor.md` — schema 变更
- `sop/Backend amends.md` — 这些发现所暗示的后端/API 变更

在实现**之前或之中**合并它们；不要对着已知不足的 schema/API 硬建。

### 合并 schema 修订

若存在 `prisma/request-for-refactor.md`：

1. 读完该文件中的每条问题。
2. 把 **blocking** 项应用到 `prisma/schema.prisma`（以及需要时的相关 prisma 文件，如 `comments.sql`）。
3. 对小、可逆且连贯 API 所需的 **recommended** 项一并应用；否则在实现说明中记录推迟（不要靠保留请求文件来推迟）。
4. 更新 `prisma/seed.ts`，使其仍匹配修订后的 schema。
5. 完成后**删除** `prisma/request-for-refactor.md`。

### 合并后端修订

若存在 `sop/Backend amends.md`：

1. 读完每条请求的 API/行为变更。
2. 把这些修订折入 `backend/` 下的实现（并与合并后的 schema/seed 保持一致）。
3. 与 `sop/Backend implementation prompt.md` 冲突时，优先按修订调整设计——正确性上 seed/schema 压力优先。
4. 完成后**删除** `sop/Backend amends.md`。

## 后端

确保仓库可用 pnpm 安装并运行。

在 `/api/v1/` 下实现后端 API。

## SOP 驱动的提交

**随本步骤演进**提交——每完成一块连贯切片（产物已写出、某条路由/功能已抽出、某个 mock 已替换、某子集测试已绿等）。**不要**把整步工作拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop060]` 开头。见本 SOP 包中的 `CHECKPOINT.md`。
