# 实现后端

检出 `sop/Backend implementation prompt.md` 并在 `backend/` 下实现后端。

## Prisma 包

先检查既有 `prisma/` 目录。至少期望：

- `prisma/schema.prisma`
- `prisma/seed.ts`（若已撰写）
- `prisma/package.json`（缺失则添加）

使用该包；不要发明第二个 Prisma 根。

## 修订合并

Seed 可能在发现相对既有后端设计提示或 `backend/` 树的缺口后留下修订请求：

- `prisma/request-for-refactor.md` — schema 变更
- `sop/Backend amends.md` — 由这些发现暗示的后端/API 变更

在实现**之前**或**同时**合并它们；不要对着已知不足的 schema/API 构建。

### 合并 schema 修订

若存在 `prisma/request-for-refactor.md`：

1. 阅读该文件中的每个问题。
2. 将 **blocking** 项应用到 `prisma/schema.prisma`（以及需要时的相关 prisma 文件如 `comments.sql`）。
3. 当 **recommended** 项小、可逆且对连贯 API 必要时应用；否则在实现说明中记录推迟（不要靠保留请求文件）。
4. 更新 `prisma/seed.ts` 使其仍匹配修订后的 schema。
5. 完成后**删除** `prisma/request-for-refactor.md`。

### 合并后端修订

若存在 `sop/Backend amends.md`：

1. 阅读每个请求的 API/行为变更。
2. 将这些修订折入 `backend/` 下的实现（并与合并后的 schema/seed 保持一致）。
3. 当修订冲突时，偏好调整来自 `sop/Backend implementation prompt.md` 的设计——正确性上 seed/schema 压力胜出。
4. 完成后**删除** `sop/Backend amends.md`。

## 后端

确保仓库可用 pnpm 安装并运行。

在 `/api/v1/` 下实现后端 API。

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop060]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
