# 从仓库与 PRD 创建 Prisma schema

创建：

- `prisma/schema.prisma`
- `prisma/comments.sql`

目标 PostgreSQL。

从仓库证据推导数据模型。

设计 schema 之前，检查：

- `sop/PRD.md`
- `sop/design-inventory.md`（UI 暗示的表格/列与 mock 实体）
- `web/`
- 若存在则 `sop/figma-archive/`
- 既有 `prisma/` 文件
- mock 数据
- fixtures
- types/interfaces
- 若存在则 API/service 定义

若存在，将 `sop/PRD.md` 作为主要产品规格，但对照当前应用与设计清单核实明显矛盾。清单/mock 中表现为有填充表格/列表的实体，不应仅因 PRD 文案单薄而省略。

## 建模规则

要求：

- ID 列使用 `cuid(2)`
- 数据库表名使用 `snake_case`
- 数据库列名使用 `snake_case`
- 包含有意义的 Prisma 文档注释
- 将相关 Prisma 注释转换为 PostgreSQL `COMMENT ON` 语句
- 使用 PostgreSQL schema `<appname>`

建模仓库证据所支持的完整领域，而不仅是某一屏上立刻可见的字段。

考虑：

- 实体身份
- 生命周期/状态
- 父子关系
- 多对多关系
- 排序
- 版本/历史需求
- 媒体
- 外部引用
- 搜索/筛选模式
- 唯一性规则
- 归档/删除语义
- 时间戳
- 实际需要的可扩展性

为常见查找与搜索路径使用有用索引。

仅在领域证据支持时添加唯一约束。

跨应用标识符通常应为无数据库外键约束的标量 cuid2 字段，除非既有仓库要求明确要求关系。

支持 WorldMan 独立 vs 集成建模：自有主数据在本 schema；对等主数据保持为经 API 解析的不透明 cuid2 引用。仅当模块必须在无对等方时独立运行时，才偏好最小本地表。

当稳定关系结构明显时避免 JSON。

仅当结构确实动态、面向扩展，或其它不适合稳定关系建模时使用 JSON。

## 不确定性处理

不要仅为了让 schema 更复杂而发明领域结构。

若仓库证据不足以支撑重要建模决策：

- 选择破坏性最小、最可逆的表示
- 在有用处用 Prisma 注释记录不确定性
- 不要静默断言无支持的业务规则

本步骤不要生成 `seed.ts`。

将完成的文件直接写到：

- `prisma/schema.prisma`
- `prisma/comments.sql`
