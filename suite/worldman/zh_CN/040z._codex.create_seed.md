# 根据仓库状态创建种子数据

创建 `prisma/seed.ts`。

以现有仓库为事实来源。

编写 seed 之前，检查：

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `web/`
- 已有 fixtures
- mock 数据
- 演示数据
- 测试

在合适处复用项目中已有的稳定演示概念、名称、分类、媒体引用与代表性状态。

优先写入能使 `sop/TUC.md` / `sop/ECS.md` 场景可复现的 seed 行。
## Seed 目标

Seed 应不止填充行。它应充分锻炼领域，以支持：

- 本地开发
- UI 集成
- API 测试
- Playwright 工作流
- 搜索/过滤/排序演示
- 状态转换测试

在适用处包含：

- 多个代表性实体
- 多个分类/类型
- 现实关系
- 不同生命周期状态
- 启用/停用示例
- 草稿/已发布/已完成/已取消示例
- 父子关系
- 多对多关系
- 历史/版本示例
- 空或可选字段示例
- 对测试有用的边界示例
- 可区分搜索/过滤的值
- 日期/时间变化
- 演示媒体 URL
- 图片 URL
- 相关时的音视频 URL
- 相关时的文件/附件

优先使用确定、可读的演示值，而不是随机数据。

在测试可能需要可预测记录处，使用稳定标识符或稳定查找键。

## Schema 压力测试

设计现实 seed 场景时，主动评估当前 schema 能否表达已文档化的产品。

本步不要修改或默默重新设计 `prisma/schema.prisma`。

若 seed 设计暴露出 schema 无法充分表达重要产品需求、关系、生命周期状态、约束、历史案例或现实测试场景，同时创建 `prisma/request-for-refactor.md`。

每个问题包含：

- 受影响模型
- 观察到的仓库/产品证据
- 暴露问题的具体 seed 场景
- 当前 schema 为何不足
- 严重程度：blocking | recommended
- 建议的最小 schema 变更
- 对现有数据的影响
- 对 seed 逻辑的影响
- 对后端/API 的影响
- 对自动化测试的影响

不要自动应用所提议的 schema 变更。

若不需要 schema 变更，不要创建 `request-for-refactor.md`。

本步最终交付物为：

- `prisma/seed.ts`
- `prisma/request-for-refactor.md`（可选）
