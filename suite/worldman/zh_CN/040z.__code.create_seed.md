# 从仓库状态创建 seed 数据

创建 `prisma/seed.ts`。

以既有仓库为真相源。

写 seed 之前，检查：

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/design-inventory.md`（尤其是 **Mock / demo data sources**）
- `sop/seed-coverage.md`（若在更新既有 seed）
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `sop/figma-archive/`（若存在）
- `web/`
- 既有 fixtures
- mock 数据
- demo 数据
- 测试

## 优先提取，少发明

只要 schema 能表达，seed 行应**保留 Figma / web demo 数据**：

1. 定位 `sop/design-inventory.md` 中列出的每个 mock/demo/fixture 来源，以及仍在 `web/` 或 `sop/figma-archive/` 下的其它来源。
2. 名称/形态对齐时，逐字段映射到 Prisma 模型。
3. 复用项目中已有的稳定 demo 概念、名称、分类、媒体引用与代表性状态。
4. **保持 media ↔ text 配对**（图片/海报与其标题、说明、作者、价格等）。不要把 Figma 图片挂到另一条发明标题上，也不要为已有 demo 名发明新的主图。
5. 仅为填补 `sop/TUC.md` / `sop/ECS.md` 或 schema 必需关系的缺口才发明新行——绝不要用更薄的“干净”样本集替换既有 demo 内容。覆盖报告中标注每条发明行。
6. 若 mock 实体无法装进 schema，写 `prisma/request-for-refactor.md`（或记在 Open Questions），而不是静默丢掉 demo。
7. 若 Figma / mock 数据本身看起来有问题（重复名、坏 URL、与相邻 UI 文案矛盾的占位 lorem、明显属于另一张卡片的图），**不要在 seed 里静默“修好”**。优先原样提取，再记录 `figma-suspect` 差异（见下）。仅当 schema 或运行时否则会坏掉时，seed 才可带最小修正——且该修正必须写明。

优先让 seed 行能复现 `sop/TUC.md` / `sop/ECS.md` 场景，**同时**不擦掉 Figma demo 集。

## Seed 覆盖报告（必需）

写出或更新 `sop/seed-coverage.md`：

```markdown
# Seed coverage vs web / Figma mocks

| mock source | entity / concept | mock examples (count or names) | seed model / rows | status | media↔text |
|-------------|------------------|--------------------------------|-------------------|--------|------------|
| …           | …                | …                              | …                 | matched / seed-enriched / figma-suspect / schema-blocked / missing | ok / mismatched / n/a |

## Discrepancy log (required when anything is not `matched`)

| id | status | evidence (mock path / UI) | seed choice | why (figma issue vs seed enrichment vs schema) |
|----|--------|---------------------------|-------------|------------------------------------------------|
| …  | …      | …                         | …           | …                                              |
```

状态含义：

- `matched` — seed 行保留了 mock 的标识字段与媒体配对
- `seed-enriched` — 为 TUC/ECS/schema 额外加了行/字段；Figma 行仍在
- `figma-suspect` — mock/导出数据看起来不一致或有误；已点名，未静默改写
- `schema-blocked` — 尚无法表达；指向 `request-for-refactor` / Open Questions
- `missing` — mock 面未入 seed（关键项会阻止 `080` 删除 mock）

每个清单中的 mock 来源都应出现。缺口与差异必须显式。步骤 `080` 会拒绝删除仍有未覆盖关键 `missing` / 未解决 `schema-blocked` 缺口的 mock。

## Seed 目标

Seed 应做的不只是填行。它应充分锻炼领域，以支撑：

- 本地开发
- UI 集成
- API 测试
- Playwright 工作流
- 搜索/筛选/排序演示
- 状态迁移测试

在适用处包含：

- 多个代表性实体
- 多个分类/类型
- 真实关系
- 不同生命周期状态
- 启用/停用示例
- 草稿/已发布/已完成/已取消示例
- 父子关系
- 多对多关系
- 历史/版本示例
- 空值或可选字段示例
- 对测试有用的边界示例
- 可区分搜索/筛选的取值
- 日期/时间变化
- demo 媒体 URL
- 图片 URL
- 相关处的音频/视频 URL
- 相关处的文件/附件

优先确定、可读的 demo 值，而不是随机数据。

测试可能需要可预测记录时，使用稳定标识或稳定查找键。

本步不要修改或静默重设计 `prisma/schema.prisma`。

交付物：`prisma/seed.ts` 与 `sop/seed-coverage.md`。

<optional title="Also request schema / backend amends?">
若本次 seed 工作暴露出与既有后端设计提示或既有 `backend/` 树的缺口，写出所需修订文件（省略不必要的）：

1. **Schema** — 当 `schema.prisma` 无法表达需求、关系、生命周期状态、约束、历史案例或真实测试时，写 `prisma/request-for-refactor.md`。包含受影响模型、证据、seed 场景、为何不足、严重度（blocking | recommended）、最小改动，以及对数据 / seed / API / 测试的影响。

2. **Backend** — 当后端设计提示或既有 `backend/` 需要 API/行为变更以匹配这些发现时，写 `sop/Backend amends.md`。

本步**不要**应用变更。后续实现应合并这些文件，然后删除它们。
</optional>

## SOP 驱动的提交

**随本步骤演进**提交——每完成一块连贯切片（产物已写出、某条路由/功能已抽出、某个 mock 已替换、某子集测试已绿等）。**不要**把整步工作拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop040]` 开头。见本 SOP 包中的 `CHECKPOINT.md`。
