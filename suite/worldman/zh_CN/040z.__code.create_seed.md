# 从仓库状态创建 seed 数据

创建 `prisma/seed.ts`。

以既有仓库为真相来源。

撰写 seed 之前，检查：

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/design-inventory.md`（尤其 **Mock / demo data sources**）
- `sop/seed-coverage.md`（若在更新既有 seed）
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `sop/figma-archive/`（若存在）
- `web/`
- 既有 fixtures
- mock 数据
- demo 数据
- 测试

## 优先提取而非发明

只要 schema 能表达，seed 行应**保留 Figma / web demo 数据**：

1. 定位 `sop/design-inventory.md` 中列出的每个 mock/demo/fixture 来源，
   以及仍在 `web/` 或 `sop/figma-archive/` 下的其它来源。
2. 当名称/形状对齐时，逐字段映射到 Prisma 模型。
3. 复用项目中已有的稳定 demo 概念、名称、分类、媒体引用与
   代表性状态。
4. 仅在 `sop/TUC.md` / `sop/ECS.md` 或 schema 必需关系要求填补缺口时发明新行——
   绝不要用更瘦的“干净”样本集替换既有 demo 内容。
5. 若某 mock 实体无法适配 schema，提交 `prisma/request-for-refactor.md`
   （或记在 Open Questions 下），而不是静默丢掉 demo。

偏好能使 `sop/TUC.md` / `sop/ECS.md` 场景可复现的 seed 行。

## Seed 覆盖报告（必需）

写出或更新 `sop/seed-coverage.md`：

```markdown
# Seed coverage vs web / Figma mocks

| mock source | entity / concept | mock examples (count or names) | seed model / rows | gap |
|-------------|------------------|--------------------------------|-------------------|-----|
| …           | …                | …                              | …                 | none / missing … |
```

每个清单 mock 来源都应出现。缺口必须显式。步骤 `080`
将拒绝删除仍有未覆盖关键缺口的 mock。

## Seed 目标

Seed 应不止填充行。它应充分锻炼领域，以支持：

- 本地开发
- UI 集成
- API 测试
- Playwright 工作流
- 搜索/筛选/排序演示
- 状态转换测试

在适用处包含：

- 多个代表性实体
- 多个分类/类型
- 真实关系
- 不同生命周期状态
- 活跃/非活跃示例
- 草稿/已发布/已完成/已取消示例
- 父子关系
- 多对多关系
- 历史/版本示例
- 空或可选字段示例
- 对测试有用的边界示例
- 可区分搜索/筛选的值
- 日期/时间变化
- demo 媒体 URL
- 图片 URL
- 相关处的音频/视频 URL
- 相关处的文件/附件

偏好确定、可读的 demo 值，而非随机数据。

在测试可能需要可预测记录处，使用稳定标识符或稳定查找键。

本步骤中不要修改或静默重设计 `prisma/schema.prisma`。

交付物：`prisma/seed.ts` 与 `sop/seed-coverage.md`。

<optional title="Also request schema / backend amends?">
若本 seed 工作暴露出相对既有后端设计提示或既有
`backend/` 树的缺口，写出所需修订文件（省略不必要者）：

1. **Schema** — 当 `schema.prisma` 无法表达需求、关系、生命周期状态、约束、历史
   情形或真实测试时，写 `prisma/request-for-refactor.md`。包含受影响模型、证据、
   seed 场景、为何不足、严重程度（blocking | recommended）、最小变更，以及对
   数据 / seed / API / 测试的影响。

2. **Backend** — 当后端设计提示或既有 `backend/` 需要 API/行为变更以匹配这些发现时，
   写 `sop/Backend amends.md`。

此处**不要**应用变更。后续实现应合并这些文件然后删除它们。
</optional>

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop040]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
