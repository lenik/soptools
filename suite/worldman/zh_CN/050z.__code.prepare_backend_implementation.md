# 准备基于仓库的后端实现

这是本应由 GPT 步骤生成后端实现提示时的 Codex 回退。

因为你已在仓库内操作，不要生成意在粘贴回 Codex 的提示。

相反，检查仓库并准备具体实现计划，然后让仓库为后端实现步骤就绪。

至少审阅：

- `sop/PRD.md`
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `sop/TODO.md`（若存在）
- `prisma/schema.prisma`
- `prisma/seed.ts`
- `web/`
- `package.json`
- `pnpm-workspace.yaml`
- 既有 `backend/`

亦检查：

- web 路由
- 前端 data/service 抽象
- mock 数据
- 既有请求/响应形状
- 领域枚举与状态转换
- 搜索/筛选/排序行为
- 批量操作
- 跨实体导航
- 看似可超出当前 UI 复用的功能

抽取共享工具或支撑类时，优先使用已在 `sop/` 下捕获的需求与场景（`PRD.md`、`TUC.md`、`NTC.md`、`ECS.md`）。

计划条目完成或推迟时保持 `sop/TODO.md` 状态最新。
创建 `docs/backend-implementation-plan.md`。

## 后端假设

目标：

- `pnpm`
- Node.js
- TypeScript

API 前缀：`/api/v1/`

后端必须暴露有用的领域能力，而不仅是当前 web UI 所需的最小端点。

对每个领域资源，评估是否有意义地需要：

- CRUD
- list
- detail
- search
- lookup
- autocomplete
- filtering
- sorting
- pagination
- batch retrieval
- bulk create/update/delete
- relation traversal
- tree traversal
- state transitions
- history
- version access
- validation
- statistics
- aggregation
- import
- export
- media operations
- external reference resolution

不要机械地为每个模型规定每种能力。

计划应定义：

- 后端架构
- 领域/服务边界
- 路由组
- 校验策略
- 错误模型
- 序列化约定
- 分页约定
- 筛选/排序约定
- 资源能力
- 领域特定操作
- 批量操作语义
- 测试策略
- 与 web/ 的集成关注点
- 实现顺序

偏好分离：

- route/controller 层
- validation
- service/领域逻辑
- data access
- 共享错误
- API serialization

不要把领域逻辑直接放在路由处理器中。

## 基于仓库的缺口处理

若 `sop/PRD.md`、`schema.prisma`、seed 数据与 web 应用不一致：

- 在 `docs/backend-implementation-plan.md` 中记录矛盾
- 标明哪个来源看似权威以及为何
- 选择最小可逆的实现假设
- 不要静默重设计 schema 或产品

若存在 `prisma/request-for-refactor.md` 或 `sop/Backend amends.md`，审阅它们并把相关阻塞项折入实现计划。Schema 与后端修订在实现后端时应用，届时应合并这些文件然后删除它们。

除非调用本文件的工作流明确要求把规划与实现合并，否则本步骤不要实现后端。

来源冲突时，用户可见面偏好 `sop/design-inventory.md` + 当前 `web/` 行为，持久化形状偏好 `schema.prisma` / seed——记录冲突，而不是为迁就稀疏 API 计划而削薄 UI。

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop050]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
