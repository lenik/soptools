# 从仓库证据创建 PRD

## WorldMan 架构（先读）

撰写 PRD 之前，先介绍并应用本模块架构：

- WorldMan 应用是轻量微服务风格模块：每个既可**完全独立运行**，也可与对等应用**集成**。
- **独立**：应用可为共享基础数据拥有**最小本地表**（例如仅联系人姓名+电话）。专用对等应用（例如 contacts）可对同一概念建模得远更完整。
- **集成**：对等主数据仅存为**不透明 cuid2 引用**，并通过该对等方的 API 解析——不是跨库外键。
- 主数据主键使用 **`cuid(2)`**，以便身份在独立与集成部署间保持稳定。
- 标准布局：`prisma/`、`backend/`、`web/`、`web-e2e/`、可选 `mobile/` / `mobile-e2e/`、`sop/`、`docs/`、`docker/`、`i-local/`、`i-medium/`、`worldman.json`。
- 部署为直接进程、Apache/Nginx 反代或容器。基准端口 `N` 来自 `wm port -n <name>`（HTTPS = HTTP+1，bridge web `80`/`443` 除外；见 SOP README）。

在证据支持处把这些约束反映进 PRD。

从仓库本身重建产品规格。

- `web/`

- `docs/`
- `prisma/`
- `README*`
- `package.json`
- `worldman.json`

（若它们存在）。

- 路由与页面
- 导航结构
- 页面标题与标签
- 表单与字段
- 表格与列
- 对话框、sheet、drawer 与菜单
- 搜索/筛选/排序控件
- CRUD 操作
- 批量操作
- 状态/status 控件
- 媒体使用
- mock 数据
- fixtures
- 常量/枚举
- local-storage/session-storage 使用
- 校验消息
- 空状态
- 错误状态

## UI 结构 vs 导出噪音

将 `sop/design-inventory.md` 视为**导航与表格 UI 结构的权威**
（其中列出的路由、页签、主要 chrome、对话框）。

- 每个状态为 `kept` / `moved` 的清单条目都是要在 PRD 中记录的产品面
  （工作流 + 验收），不是可选装饰。
- 不得把已列出的页签/路由降级为“意外导出”，除非把清单更新为
  `dropped:<reason>` 或带证据的 `dead`/`scaffold`。
- “意外设计导出细节”适用于无标签桩件、重复脚手架 chrome，或清单已标
  `dead`/`scaffold` 的控件——不适用于带真实标签/内容的独立屏幕或页签面板。

从重复的、语义有意义的证据推断其余产品意图。

## 证据优先级

来源冲突时，按此顺序偏好：

1. `sop/` 下既有显式产品文档（尤其 `sop/PRD.md`）然后 `docs/`
2. 路由、页签、chrome 与已列对话框方面的 `sop/design-inventory.md`
3. 既有 Prisma/领域定义
4. 已实现的用户可见行为
5. 稳定的 mock/fixture 数据结构
6. 孤立标签、占位文案或死导出/脚手架控件（仅当未在清单中 kept）

不要仅为了让 PRD 看起来完整而发明需求。

若重要需求无法从仓库证据确定，记在 **Open Questions / Unresolved Requirements** 下。

不要通过询问澄清来阻塞任务。

## PRD 要求

PRD 应适合实现与后续验收测试。

在证据支持处覆盖：

- 产品概述
- 目标
- 范围
- 范围外
- 术语
- 用户角色
- 领域概念
- 核心实体
- 实体关系
- 业务规则
- 生命周期/状态转换
- CRUD 行为
- 搜索
- 筛选
- 排序
- 相关处的分页
- 批量操作
- 相关处的导入/导出
- 媒体
- 相关处的历史/审计行为
- 外部引用
- 校验规则
- 删除/归档行为
- 空状态
- 错误行为
- 重要边界情况
- 主要 UI 工作流
- 非功能期望
- WorldMan 独立 vs 集成模型
- Open Questions / Unresolved Requirements

对每条实质性推断需求，写得足够清晰，使另一开发者能实现或测试它。

在证据支持时记录 WorldMan 约束：

- 本模块的独立 vs 集成运行
- 哪些实体是自有主数据，哪些是对等模块的不透明 cuid2 引用
- 主数据主键的 `cuid(2)` 身份
- 相关时经 `wm port -n <name>` 的部署/端口期望（HTTPS = HTTP+1，bridge `80`/`443` 除外）

在文档化时不要重设计既有产品。

当证据或提示产生可测试材料时，亦在 `sop/` 下初始化或更新：

- `TODO.md` — 剩余重建 / 实现任务；保持状态最新
- `TUC.md` — 测试用例参考集
- `NTC.md` — 反用例 / 负面测试用例
- `ECS.md` — 边界场景

这些文件供后续 e2e 工作流与工具/支撑类工作使用。

将完成的产物直接写到 `sop/PRD.md`。

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop020]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
