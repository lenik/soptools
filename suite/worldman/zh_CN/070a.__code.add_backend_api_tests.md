# 添加后端 API 测试

添加自动化后端 API 测试。

测试应覆盖真实公共 API 行为，而不是内部实现细节。

在适用处覆盖：

- create
- read
- update
- delete/archive
- list
- search
- filter
- sort
- pagination
- lookup
- relations
- tree operations
- state transitions
- validation failures
- not found
- conflicts
- duplicate prevention
- bulk operations
- history/version behavior
- domain-specific operations

同时测试从下列来源发现的重要边界情况：

- `sop/PRD.md`
- `sop/TUC.md`（若存在）
- `sop/NTC.md`（若存在）
- `sop/ECS.md`（若存在）
- `prisma/schema.prisma`
- `prisma/seed.ts`

用户提示或实现工作暴露新用例时，尽快更新 `sop/TUC.md`、`sop/NTC.md`、`sop/ECS.md`。
测试应使用确定的测试数据。

**测完随手清理。** 向共享库（开发 / 预发 / 长期本地 Postgres）插入行的后端/API 测试，必须在 `afterEach` / `afterAll` / fixture 拆卸中删除这些行——失败时也要删。建议用唯一标记（前缀、标签或 `createdBy=test-…`），以便选择性清理且不会误删 seed/demo。在共享库里留下上百条测试实体（例如大量 “Ava …” 练习记录）本身就是缺陷。

运行后端测试。

修复后端实现与测试，直到后端测试套件通过。

在把前端集成问题当成前端问题之前，后端测试必须先通过。

套件结束后（无论通过或失败），抽查是否还有仅测试用的残留行；若有污染，先删干净并加固拆卸逻辑，再进入下一步。

## SOP 驱动的提交

**随本步骤演进**提交——每完成一块连贯切片（产物已写出、某条路由/功能已抽出、某个 mock 已替换、某子集测试已绿等）。**不要**把整步工作拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop070]` 开头。见本 SOP 包中的 `CHECKPOINT.md`。
