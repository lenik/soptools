# 根据仓库与 PRD 创建 Prisma schema

创建：

- `prisma/schema.prisma`
- `prisma/comments.sql`

目标为 PostgreSQL。

请从仓库证据推导数据模型。

设计 schema 之前，检查：

- `sop/PRD.md`
- `web/`
- 已有 `prisma/` 文件
- mock 数据
- 测试夹具（fixtures）
- 类型/接口
- 若存在的 API/服务定义

若存在 `sop/PRD.md`，将其作为主要产品规格，但对照当前应用核对明显矛盾。

## 建模规则

要求：

- ID 列使用 `cuid(2)`
- 数据库表名使用 `snake_case`
- 数据库列名使用 `snake_case`
- 包含有意义的 Prisma 文档注释
- 将相关 Prisma 注释转换为 PostgreSQL `COMMENT ON` 语句
- 使用 PostgreSQL schema `<appname>`

建模仓库证据所支持的完整领域，而不仅是某一屏上立刻可见的字段。

考虑：

- 实体身份
- 生命周期/状态
- 父子关系
- 多对多关系
- 排序
- 版本/历史需求
- 媒体
- 外部引用
- 搜索/过滤模式
- 唯一性规则
- 归档/删除语义
- 时间戳
- 确有需要时的可扩展性

为常见查找与搜索路径建立有用索引。

仅在领域证据支持时添加唯一约束。

跨应用标识通常应为无数据库外键约束的标量 cuid2 字段，除非现有仓库要求明确需要关系。

支持 WorldMan 独立 vs 集成建模：本模块拥有的主数据留在本 schema；对等主数据保持为经 API 解析的不透明 cuid2 引用。仅当模块必须在无对等应用时独立运行时，才优先使用最小本地表。

当稳定关系结构已明显时，避免 JSON。

仅在结构确实动态、面向扩展、或不适合稳定关系建模时使用 JSON。

## 不确定性处理

不要仅为让 schema 更「丰富」而发明领域结构。

若仓库证据不足以支撑重要建模决策：

- 选择破坏性最小、最可逆的表示
- 在有用处用 Prisma 注释记录不确定性
- 不要默默断言无证据的业务规则

本步不要生成 `seed.ts`。

将完成文件直接写入：

- `prisma/schema.prisma`
- `prisma/comments.sql`
