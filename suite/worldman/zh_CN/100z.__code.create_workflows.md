## 来源优先级

确定预期行为时，偏好：

1. `sop/PRD.md`
2. 若存在则 `sop/TUC.md` / `sop/NTC.md` / `sop/ECS.md`
3. `schema.prisma` 中的显式领域规则
4. 稳定的后端/API 行为
5. 已实现的用户可见行为
6. seed 场景与 fixtures
7. 孤立 UI 产物或死导出/脚手架控件

不要仅为迁就明显实现缺陷而改写预期工作流。

不要为不支持的产品功能发明工作流。

若重要行为未解决，在相关工作流或最终未解决小节中加入简短的 **Unresolved behavior** 说明，而不是捏造规则。

## 工作流目标

这些工作流是 Playwright 的行为验收规格。

它们不是 Playwright 源码。

使用可读的工作流风格伪代码。

以有限但广泛的功能覆盖覆盖产品。

在适用处包含：

- 路由访问
- 导航
- 创建流
- 编辑流
- 删除/归档流
- 详情视图
- 搜索
- 筛选
- 排序
- 分页
- 页签
- 对话框
- sheets
- 菜单
- 上下文菜单
- 批量操作
- 状态转换
- 校验失败
- 取消路径
- 空状态
- 确认流
- 媒体交互
- 导入/导出
- 跨实体导航
- 重要错误路径
- 重要边界情况

偏好真实端到端工作流，而非每个按钮一个工作流。

在能使场景确定可复现处使用 seed 数据。

## 分支语法

分支应描述真实条件。

除非这些术语在领域中确实有意义，避免如 `{correct/error}` 的泛化分支。

偏好：

```text
Login
    enter phone
    enter password

    if password matches:
        submit
        dashboard opens

    if password does not match:
        submit
        login remains open
        error message appears
```

工作流可使用：

- precondition
- sequence
- selection
- branch
- repeat
- expected visible result

保持实用、可读，并可直接在 Playwright 中实现。

将完成的产物直接写到 `web-e2e/workflows.md`。

当清单支持的页签表面承载不同用户任务时，包含锻炼这些页签的工作流——
不要把它们折叠成从不打开次级页签的单一 happy path。

## SOP 驱动的提交

**随本步骤演进**提交——在每个连贯切片之后（写出产物、
抽出一条路由/功能、替换一个 mock、子集测试转绿，…）。
**不要**把整个步骤拖到步骤末尾一次提交。

SOP 驱动的主题必须以 `[sop100]` 开头。见本 SOP 包中的
`CHECKPOINT.md`。
