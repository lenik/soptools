# Create PRD from repository evidence

## WorldMan architecture (read first)

Before writing the PRD, introduce and apply this module architecture:

- WorldMan apps are lightweight microservice-style modules: each can run **fully independently**, or **integrate** with peer apps.
- **Standalone**: the app may own a **minimal local table** for shared basics (for example contact name + phone only). A dedicated peer app (for example contacts) may model the same concept far more completely.
- **Integrated**: peer master data is stored only as an **opaque cuid2 reference** and resolved through that peer’s API — not a cross-database foreign key.
- Master-data primary keys use **`cuid(2)`** so identities stay stable across standalone and integrated deployments.
- Standard layout: `prisma/`, `backend/`, `web/`, `web-e2e/`, optional `mobile/` / `mobile-e2e/`, `sop/`, `docs/`, `docker/`, `i-local/`, `i-medium/`, `worldman.json`.
- Deploy as direct processes, Apache/Nginx reverse proxy, or containers. Port base `N` from `wm port -n <name>` (HTTPS = HTTP+1 except bridge web `80`/`443`; see SOP README).

Reflect these constraints in the PRD where evidence supports them.

## Reconstruct from the repository

Create or replace `sop/PRD.md`.

Reconstruct the product specification from the repository itself.

Before writing the PRD, inspect the repository systematically.

At minimum review:

- `web/`
- `sop/`
- `docs/`
- `prisma/`
- `README*`
- `package.json`
- `worldman.json`

if they exist.

Inspect the web application for:

- routes and pages
- navigation structure
- page titles and labels
- forms and fields
- tables and columns
- dialogs, sheets, drawers and menus
- search/filter/sort controls
- CRUD actions
- bulk actions
- state/status controls
- media usage
- mock data
- fixtures
- constants/enums
- local-storage/session-storage usage
- validation messages
- empty states
- error states
- comments/TODOs that reveal intended behavior

Do not treat every accidental design-export detail as a product requirement.

Infer product intent from repeated, semantically meaningful evidence.

## Evidence priority

When sources disagree, prefer in this order:

1. existing explicit product documentation under `sop/` (especially `sop/PRD.md`) then `docs/`
2. existing Prisma/domain definitions
3. implemented user-visible behavior
4. stable mock/fixture data structures
5. isolated labels, placeholder copy, or dead export/scaffold controls

Do not invent requirements merely to make the PRD look complete.

If an important requirement cannot be determined from repository evidence, record it under **Open Questions / Unresolved Requirements**.

Do not block the task by asking for clarification.

## PRD requirements

The PRD should be suitable for implementation and later acceptance testing.

Cover, where supported by evidence:

- Product overview
- Goals
- Scope
- Out of scope
- Terminology
- User roles
- Domain concepts
- Core entities
- Entity relationships
- Business rules
- Lifecycle/state transitions
- CRUD behavior
- Search
- Filter
- Sort
- Pagination where relevant
- Bulk operations
- Import/export where relevant
- Media
- History/audit behavior where relevant
- External references
- Validation rules
- Deletion/archive behavior
- Empty states
- Error behavior
- Important edge cases
- Main UI workflows
- Non-functional expectations
- WorldMan standalone vs integration model
- Open Questions / Unresolved Requirements

For each material inferred requirement, make it clear enough that another developer can implement or test it.

Document WorldMan constraints when evidence supports them:

- standalone vs integrated operation of this module
- which entities are owned master data vs opaque cuid2 references to peer modules
- `cuid(2)` identity for master-data primary keys
- deployment/port expectations via `wm port -n <name>` when relevant (HTTPS = HTTP+1 except bridge `80`/`443`)

Do not redesign the existing product while documenting it.

Also initialize or update under `sop/` when evidence or prompts yield testable material:

- `TODO.md` — remaining reconstruction / implementation tasks; keep status current
- `TUC.md` — test use-case reference set
- `NTC.md` — negative / anti test cases
- `ECS.md` — edge-case scenarios

These files feed later e2e workflows and tool/support-class work.

Write the completed artifact directly to `sop/PRD.md`.
