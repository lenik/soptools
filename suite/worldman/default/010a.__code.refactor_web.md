## Localize Figma demo assets

Figma Make prototypes often hotlink remote demo media (images, fonts, audio,
video, Lottie, and similar). During this refactor, make the UI self-contained:

1. Scan `web/` for absolute `http(s)://` URLs used as demo assets (CSS
   `@import` / `@font-face`, `<img>` / `<audio>` / `<video>`, background
   URLs, fetch/import of media, etc.).
2. Download each asset **as-is** under `web/assets/`, grouped by kind when
   useful:
   ```text
   web/assets/
       images/
       fonts/
       audio/
       video/
       …
   ```
   When downloading, hosts such as Google / Google Fonts / gstatic, Facebook /
   fbcdn, and similar **must** use the local HTTP proxy `http://localhost:8118`
   (via `http_proxy` / `https_proxy`, or curl/wget `--proxy`). Do not attempt
   long direct fetches to those hosts. For other CDNs, try direct first; if the
   fetch fails, retry through the proxy until the real file is obtained. Do not
   give up or substitute fake assets.
3. Rewrite every reference to the local path or module import. Prefer stable,
   descriptive filenames; keep any license or attribution notes that shipped
   with the asset.
4. For **fonts** (hard rules — Google Fonts / gstatic are often unreachable
   without a proxy):
   - **Keep the original family.** Do not substitute Inter / system-ui / a
     theme-pack face. Same `font-family`, weight, and style in CSS.
   - **Reuse before download**, in order:
     1. already under `web/assets/fonts/`
     2. same family (+ weight/style when distinguishable) under
        `$HOME/.cache/fonts/`
     3. a matching installed face under `/usr/share/fonts/` or
        `$HOME/.local/share/fonts/` — **copy** that file into the project (do
        not leave a machine-only path in committed CSS)
   - If none of the above has the **same-name** face, **must download** the
     real remote `@font-face` file. Google / Google Fonts / gstatic **must**
     go through `http://localhost:8118`. Do not skip, stub, or “approximate”
     with another font because the CDN timed out.
   - Write the file into **both**:
     - project: `web/assets/fonts/…` (what the app ships)
     - cache: `$HOME/.cache/fonts/…` (shared across projects)
   - Cache layout mirrors `/usr/share/fonts` by format / family, e.g.:
     ```text
     $HOME/.cache/fonts/
         truetype/<FamilyName>/…
         opentype/<FamilyName>/…
         woff/<FamilyName>/…          # .woff / .woff2
     ```
   - Update `sop/design-inventory.md` → Typography when paths change but
     families stay.
5. Do not leave demo CDN / stock-media hotlinks in committed source. Skip
   non-asset API endpoints and intentional third-party integrations.

**Licensing and authenticity (important):** Hotlinks supplied in Figma
prototypes usually carry very permissive terms. For example, Unsplash photos
use the [Unsplash License](https://unsplash.com/license): free for personal and
commercial use, no payment, no photographer permission, and no attribution
required (also discussed
[here](https://www.zhihu.com/question/50969084)). That is especially friendly
for development and prototype testing. This app is not a stock-photo gallery
platform and does not compete with such services. **Do not over-interpret
license constraints.** Do not skip downloads or replace real media with
placeholders, solid color blocks, fake images, or other substitutes — save the
actual remote assets into `web/assets/`.

## Page extraction

Extract route-level pages from large or monolithic TSX files when appropriate.

Prefer structure based on responsibility:

```text
src/
    pages/
    features/
    components/
    hooks/
    services/
    lib/
```

### Directory roles (Vite + React — not Next.js)

| Directory | Role |
|-----------|------|
| `pages/` | **Route boundary** — one entry module per navigable screen (router + route-smoke enumeration) |
| `features/` | Page-specific UI, state, and domain chunks |
| `components/` | Reusable UI shared across routes/features |

Rules:

- Thin `pages/FooPage.tsx` re-exports are allowed **only** when the real page
  body lives under `features/` (e.g. `features/foo/…`).
- Do **not** park complete page implementations under `components/` and leave
  `pages/` as empty re-exports of those components.
- When splitting a monolithic screen that contains tabs, keep **all** tabs
  reachable. Prefer one route with internal tabs, or one child route per tab —
  update `sop/design-inventory.md` either way. Never delete tab content because
  the file was “too long”.

Oversized files **must** be split. A file that is too long usually means the structure is wrong: missing decentralization through services, discovery, and similar mechanisms, and/or tooling/support code that should be extracted into dedicated external source files.

Split according to:

- route boundary
- feature boundary
- state ownership
- reusable UI responsibility
- domain operation
- shared services / discovery / tool support extracted to dedicated modules

Preserve the existing visual design and interaction model unless a structural change is necessary.

## UI testability refactor

Refactor UI logic to make automated testing and maintenance easier.

Business logic must not live directly inside anonymous JSX callbacks.

Anonymous callbacks may only:

- forward arguments
- extract event values
- adapt an event into a named handler call

Bad:

```tsx
<button
    onClick={async () => {
        setLoading(true)
        await api.deleteItem(item.id)
        refresh()
        setLoading(false)
    }}
>
```

Preferred:

```tsx
async function performDeleteItem(id: string) {
    ...
}

function handleDeleteItemClick(id: string) {
    void performDeleteItem(id)
}
```

For event-based behavior, separate event extraction from event-independent behavior when practical.

Example:

```tsx
function performSeek(timestamp: number) {
    ...
}

function handleTimelineClick(event: MouseEvent) {
    const timestamp = extractTimestamp(event)
    performSeek(timestamp)
}
```

Use clear naming such as:

- `performCreateItem`
- `performDeleteItem`
- `performSave`
- `performSearch`
- `handleSaveClick`
- `handleFilterChange`
- `handleDialogOpen`
- `handleDialogClose`

Avoid names tied unnecessarily to visual position such as `button1_click` unless there is no meaningful semantic name.

## Root `package.json` scripts (required)

Ensure the **repository root** is a pnpm workspace parent with common script
targets. Create or update:

- `pnpm-workspace.yaml` — include at least `.`, `web`, `backend`, `prisma`,
  `web-e2e` (add `mobile` / `mobile-e2e` when those dirs are real packages)
- root `package.json` — `private: true`, `devDependency` on `concurrently` when
  `dev` fans out, and the script table below

`web/package.json` alone is not enough: later steps and operators run from the
repo root (`pnpm dev`, `pnpm db:migrate`, `pnpm e2e`).

### Required root scripts

| Script | Forwards to | Purpose |
|--------|-------------|---------|
| `dev` | `concurrently -kic blue,green npm:dev:*` | Run all `dev:*` together |
| `dev:web` | `pnpm -C web dev` | Vite (or equivalent) web |
| `dev:backend` | `pnpm -C backend dev` | API process |
| `db:generate` | `pnpm -C prisma generate` | `prisma generate` (+ any post-link hooks) |
| `db:migrate` | `pnpm -C prisma migrate` | **`prisma migrate deploy`** — apply existing migrations (CI / prod / shared DB) |
| `db:migrate:dev` | `pnpm -C prisma migrate:dev` | **`prisma migrate dev`** — create + apply in local dev |
| `db:push` | `pnpm -C prisma db:push` | `prisma db push` when used |
| `db:seed` | `pnpm -C prisma seed` | Seed |
| `db:studio` | `pnpm -C prisma studio` | Studio |
| `e2e` | `pnpm -C web-e2e test` | Playwright (add `:smoke` / `:report` when those exist) |

Optional later (when packages exist): `mobile`, `mobile:*`, `e2e:smoke`, …

### Naming rules (do not invent duplicates)

- Prefer the **`db:*`** prefix at the **repo root** for all Prisma/database
  tasks. Do **not** also ship `prisma:generate` / `prisma:migrate` at root —
  they are the same commands under another name.
- Keep **`db:migrate`** and **`db:migrate:dev`** as **two** scripts — they are
  **not** the same:
  - `db:migrate` → `migrate deploy` (non-interactive apply)
  - `db:migrate:dev` → `migrate dev` (interactive authoring)
- Do **not** add a third alias such as `db:deploy` that only repeats
  `db:migrate`.
- Inside `prisma/package.json`, use short names the root forwards to:
  `generate`, `migrate` (= deploy), `migrate:dev`, `db:push`, `seed`,
  `studio`. Align them when you first add `prisma/package.json` (step `030` /
  `060`); in this step at least wire the root scripts so later packages plug in
  cleanly.
- `backend/package.json` may call into `../prisma` for local DX; prefer
  documenting root `pnpm db:*` as the canonical operator entry.

If root `package.json` already exists (re-run / partial tree), **merge** these
scripts without deleting unrelated ones; rename obsolete `prisma:*` root
aliases to `db:*`.
