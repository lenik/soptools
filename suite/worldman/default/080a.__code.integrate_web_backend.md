# Integrate web with backend

Connect `web/` to `backend/` so the UI uses the real API.

## Goals

- Replace demo, mock, and local-only data sources with backend APIs where that is appropriate.
- Keep the approved UI structure and visual design. Do not redesign the app just because integration is in progress.
- Introduce a clear frontend API/service layer (prefer `web/src/services/` or an equivalent client module). Avoid scattering raw `fetch()` calls across page components.
- Re-check `sop/design-inventory.md`: every `kept`/`moved` route and tab must still render its primary content after integration (not a permanent blank table because seed/API is empty).

## Seed coverage gate (before deleting mocks)

1. Read `sop/seed-coverage.md` (create/update it with `040` rules if missing),
   including the **Discrepancy log**.
2. For each mock source that feeds a user-visible list/table/detail:
   - Confirm the API + seed can return equivalent representative rows (names,
     counts, media, states) after `prisma db seed` (or the project’s seed
     command).
   - Confirm **media ↔ text** pairs still match what the Figma mock showed
     (no swapped posters/titles). `mismatched` rows need a fix or an explicit
     discrepancy entry before mock removal.
   - Status `missing` or unresolved `schema-blocked` on a critical surface is
     a gate failure. `figma-suspect` may proceed only with a logged rationale;
     `seed-enriched` is fine when the original Figma rows remain.
   - If a **critical gap** remains, either fix `prisma/seed.ts` / backend first,
     or keep a temporary local fallback for that surface and document it in
     `sop/TODO.md` + `seed-coverage.md`.
3. **Do not** remove mocks and leave the UI empty for surfaces that previously
   showed Figma demo data.

Only after the gate passes for a given source, replace that source with the API.

## UI behavior

Make sure the UI handles these cases correctly:

- loading
- empty state (only when the domain is genuinely empty — not when seed lagged)
- server error
- validation error
- not found
- conflict
- save success
- delete/archive confirmation
- refresh
- reload persistence
- search
- filter
- sort
- pagination

Prefer server-side behavior for large or reusable datasets when that fits the domain.

## When integration reveals backend issues

If integration exposes a real backend design problem, refactor the backend as needed. When backend behavior changes:

- update backend tests
- keep the public API consistent
- re-run the backend tests

## SOP-driven commits

Commit **as this step evolves** — after each coherent slice (artifact written,
one route/feature extracted, one mock replaced, a subset of tests green, …).
Do **not** defer the whole step into a single end-of-step commit.

SOP-driven subjects must start with `[sop080]`. See `CHECKPOINT.md` in this
SOP pack.
