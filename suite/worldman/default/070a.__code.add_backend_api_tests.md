# Add backend API tests

Add automated backend API tests.

Tests should cover the actual public API behavior rather than internal implementation details.

Cover, where applicable:

- create
- read
- update
- delete/archive
- list
- search
- filter
- sort
- pagination
- lookup
- relations
- tree operations
- state transitions
- validation failures
- not found
- conflicts
- duplicate prevention
- bulk operations
- history/version behavior
- domain-specific operations

Also test important edge cases discovered from:

- `sop/PRD.md`
- `sop/TUC.md` (if present)
- `sop/NTC.md` (if present)
- `sop/ECS.md` (if present)
- `prisma/schema.prisma`
- `prisma/seed.ts`

When the user prompt or implementation work reveals new cases, update `sop/TUC.md`, `sop/NTC.md`, and `sop/ECS.md` promptly.
Tests should use deterministic test data.

**Clean up after yourself.** Backend/API tests that insert rows into a shared
database (dev / staging / long-lived local Postgres) must delete those rows in
`afterEach` / `afterAll` / fixture teardown — including on failure. Prefer a
unique marker (prefix, tag, or `createdBy=test-…`) so cleanup is selective and
cannot wipe seed/demo data. Leaving hundreds of test entities (e.g. “Ava …”
practices) in the shared DB is a defect.

Run backend tests.

Fix backend implementation and tests until the backend test suite passes.

Backend tests must pass before treating frontend integration problems as frontend issues.

After the suite finishes (pass or fail), spot-check that no test-only rows
remain; if pollution is found, delete it and harden teardown before moving on.
