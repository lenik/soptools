# Create seed data from repository state

Create `prisma/seed.ts`.

Use the existing repository as the source of truth.

Before writing the seed, inspect:

- `prisma/schema.prisma`
- `sop/PRD.md`
- `sop/design-inventory.md` (especially **Mock / demo data sources**)
- `sop/seed-coverage.md` (if updating an existing seed)
- `sop/TUC.md` (if present)
- `sop/NTC.md` (if present)
- `sop/ECS.md` (if present)
- `sop/figma-archive/` (if present)
- `web/`
- existing fixtures
- mock data
- demo data
- tests

## Prefer extraction over invention

Seed rows should **preserve Figma / web demo data** whenever the schema can
express it:

1. Locate every mock/demo/fixture source listed in `sop/design-inventory.md`
   and any others still under `web/` or `sop/figma-archive/`.
2. Map those records onto Prisma models field-by-field when names/shapes align.
3. Reuse stable demo concepts, names, categories, media references, and
   representative states already present in the project.
4. Invent new rows only to fill gaps required by `sop/TUC.md` / `sop/ECS.md` or
   schema-required relations — never to replace existing demo content with a
   thinner “clean” sample set.
5. If a mock entity cannot fit the schema, file `prisma/request-for-refactor.md`
   (or note under Open Questions) rather than dropping the demo silently.

Prefer seed rows that make `sop/TUC.md` / `sop/ECS.md` scenarios reproducible.

## Seed coverage report (required)

Write or update `sop/seed-coverage.md`:

```markdown
# Seed coverage vs web / Figma mocks

| mock source | entity / concept | mock examples (count or names) | seed model / rows | gap |
|-------------|------------------|--------------------------------|-------------------|-----|
| …           | …                | …                              | …                 | none / missing … |
```

Every inventory mock source should appear. Gaps must be explicit. Step `080`
will refuse to delete mocks that still have uncovered critical gaps.

## Seed objectives

The seed should do more than populate rows. It should exercise the domain sufficiently for:

- local development
- UI integration
- API testing
- Playwright workflows
- search/filter/sort demonstrations
- state-transition testing

Include, where applicable:

- multiple representative entities
- multiple categories/types
- realistic relationships
- different lifecycle states
- active/inactive examples
- draft/published/completed/cancelled examples
- parent/child relations
- many-to-many relations
- history/version examples
- empty or optional-field examples
- boundary examples useful for testing
- search/filter-distinguishable values
- date/time variations
- demo media URLs
- image URLs
- audio/video URLs where relevant
- files/attachments where relevant

Prefer deterministic, readable demo values over random data.

Use stable identifiers or stable lookup keys where tests may need predictable records.

Do not modify or silently redesign `prisma/schema.prisma` during this step.

Deliverable: `prisma/seed.ts` and `sop/seed-coverage.md`.

## SOP-driven commits

Commit **as this step evolves** — after each coherent slice (artifact written,
one route/feature extracted, one mock replaced, a subset of tests green, …).
Do **not** defer the whole step into a single end-of-step commit.

SOP-driven subjects must start with `[sop040]`. See `CHECKPOINT.md` in this
SOP pack.
