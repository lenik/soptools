# Create seed data

Create:

```text
prisma/seed.ts
```

based on the previously defined Prisma schema.

Before writing the seed, review the schema and product model against realistic demo and testing scenarios.

Do not modify or silently redesign `schema.prisma` during this step.

If seed design reveals that the existing schema cannot adequately represent an important product requirement, relationship, lifecycle state, constraint, historical case, or realistic test scenario, also create:

```text
prisma/request-for-refactor.md
```

The refactor request should describe:

- affected model(s)
- the concrete seed scenario that exposed the problem
- why the current schema is insufficient
- severity: `blocking` or `recommended`
- the smallest recommended schema change
- expected impact on existing data
- expected impact on seed logic
- expected impact on backend APIs
- expected impact on tests

Do not apply the proposed schema change automatically.

If no schema change is needed, do not create `request-for-refactor.md`.

Output the seed deliverables as a ZIP archive containing:

```text
prisma/
    seed.ts
    request-for-refactor.md   # only if needed
```

Seed data should not merely populate rows. It should exercise the domain.

Include, where applicable:

- multiple representative entities
- multiple categories/types
- realistic relationships
- different lifecycle states
- active/inactive examples
- draft/published/completed/cancelled examples where relevant
- parent/child relations
- many-to-many relations
- history/version examples
- empty or optional-field examples
- boundary examples useful for testing
- search/filter-distinguishable values
- date/time variations
- demo media URLs
- images
- audio/video URLs where relevant
- files/attachments where relevant

Seed data should be deterministic enough to support automated tests.

Prefer stable readable demo names rather than random data.
